บทสรุปผู้บริหาร

ข้อมูลเชิงลึกหลัก · Key Insight

MiroFish คือ “เครื่องจำลองความเห็นฝูงชน” (agent-based opinion simulation) ไม่ใช่เครื่องทำนายราคา — มันตอบว่า “narrative จะแพร่และจบทางไหน” ไม่ใช่ “หุ้นจะ +กี่ %”

ทั้งระบบออกแบบมาเพื่อจำลองพลวัตของ “คนหมู่มาก” ที่อ่านข้อมูลแล้ว react ต่อกัน จุดที่มันมีค่ากับงานพี่จริงคือ reflexivity layer ของงาน Japan activist/event-driven — ส่วนที่ valuation มองไม่เห็น และควรต่อยอดบน OASIS (engine ข้างใต้ ใบอนุญาต Apache-2.0) ไม่ใช่ตัว MiroFish (AGPL) เพื่อกัน moat ของ FinCouncil

อ่านรายงานนี้ใน 30 วินาที

MiroFish รับ “เมล็ดข้อมูล” (ข่าว ร่างนโยบาย รายงาน หรือแม้แต่นิยาย) มาสร้างเป็น Knowledge Graph แล้วแตกตัวละครออกมาเป็น AI agent หลายร้อย–พันตัว ที่มีบุคลิก ความจำ และพฤติกรรมของตัวเอง จากนั้นปล่อยให้ agent คุยกันบนแพลตฟอร์มจำลอง (Reddit + Twitter) หลายรอบ พี่ในฐานะ “พระเจ้า” ฉีดเหตุการณ์เข้าไปได้ แล้วระบบสรุปออกมาเป็นรายงานว่าความเห็นฝูงชนวิวัฒน์ไปทางไหน

มันถูกพิสูจน์แล้วกับ การจำลองกระแสสังคม (เคสมหา’ลัยอู่ฮั่น) และ การเดาตอนจบนิยาย (ความฝันในหอแดง) — ส่วน การเงิน “coming soon” ตามที่ repo บอกเอง คือยังไม่มีของจริงให้ลอก พี่ต้องบุกเบิกเอง รายงานนี้พาไปดูตั้งแต่หลังบ้านจริง → ตัวอย่างที่เห็นภาพ → จนถึงพิมพ์เขียววิธีต่อยอด

คำเตือนเชิงระเบียบวิธี

อย่าใช้ MiroFish ตอบ “ถือ CPALL 3 เดือนได้กี่ %” มันไม่มี engine ราคา/ปัจจัยพื้นฐาน ถ้าฝืนถาม มันจะตอบเป็น narrative ที่ฟังดูน่าเชื่อแต่ไม่ผูกกับ price dynamics จริง = ความมั่นใจปลอม ใช้มันกับคำถามที่มันเกิดมาเพื่อตอบ: “เกมความเห็นจะจบทางไหน”

MiroFish คืออะไร — แนวคิดและปัญหาที่มันแก้

คำโปรยทางการคือ “swarm intelligence engine — predicting anything” แต่ในทางปฏิบัติ MiroFish ทำสิ่งเดียวที่ชัดมาก: สร้างโลกสังคมจำลองที่มี AI agent จำนวนมาก แล้วดูว่าความเห็น/อารมณ์ของพวกเขาวิวัฒน์ไปทางไหนเมื่อมีข้อมูลใหม่เข้ามา มันคือ “กระจกเงาของฝูงชน” ที่จับ emergent behavior — สิ่งที่โผล่จากการที่ปัจเจกคุยกัน ไม่ใช่จากสูตรสำเร็จ

รากฐาน: MiroFish = OASIS + ชั้นห่อ

หัวใจสำคัญที่ต้องเข้าใจตั้งแต่ต้น: เครื่องยนต์จำลองจริง ๆ ไม่ใช่ code ของ MiroFish เอง แต่เป็น OASIS (Open Agent Social Interaction Simulations) ของทีม CAMEL-AI — และ OASIS เป็น Apache-2.0 (permissive) สิ่งที่ MiroFish เพิ่มเข้าไปคือชั้นรอบ ๆ: ตัวดูดข้อมูลเป็นกราฟ, ตัวปั้น persona, ตัวตั้งค่า, ReportAgent, และ frontend Vue — ทั้งหมดนี้ห่อด้วย AGPL-3.0 ความต่างของสองใบอนุญาตนี้คือหัวใจของคำแนะนำในข้อ 5

หลังบ้าน — สถาปัตยกรรม 5 ขั้น

วิธีคิดที่ทำให้เข้าใจง่ายที่สุด: MiroFish เป็น “สายพานการผลิต” ที่แปลง ก้อนข้อความดิบ → โลกสังคมที่มีชีวิต → รายงานทำนาย ผ่าน 5 สถานี แต่ละสถานีคือ service จริงใน backend/app/services/

ขั้นทำอะไร (ภาษาคน)บริการหลัก (code)ผลลัพธ์
1 · Graph Buildingหั่นข้อความ → สกัดเอนทิตี/ความสัมพันธ์ → สร้างกราฟความรู้text_processor · ontology_generator · graph_builderKnowledge graph บน Zep
2 · ปั้น Agentอ่านเอนทิตีในกราฟ → ปั้นเป็นตัวละครมีบุคลิกzep_entity_reader · oasis_profile_generatorpersona หลายร้อย–พันตัว
3 · ตั้งค่าอ่านโจทย์ภาษาคน → แปลงเป็นพารามิเตอร์การจำลองsimulation_config_generatorSimulationParameters (JSON)
4 · จำลองรัน OASIS สองแพลตฟอร์มพร้อมกัน หลายรอบ + ฉีดเหตุการณ์simulation_runner · simulation_ipc · scripts/run_*_simulationaction log + กราฟที่วิวัฒน์
5 · รายงานReAct agent ค้นกราฟ + สัมภาษณ์ agent → เขียนรายงานทีละส่วนreport_agent · zep_toolsรายงานทำนาย + บทสัมภาษณ์

2.1 ขั้น 1 — สร้าง Knowledge Graph จาก seed

พี่อัปโหลดไฟล์ (PDF/MD/TXT, ≤50MB) TextProcessor หั่นเป็นก้อนละ ~500 ตัวอักษร (เหลื่อม 50) จากนั้น OntologyGenerator ให้ LLM อ่านตัวอย่างเนื้อหาแล้ว “ออกแบบ schema” เองว่าในเรื่องนี้มีเอนทิตีชนิดไหน (คน/องค์กร/เหตุการณ์) สัมพันธ์กันยังไง — แล้วแปลงเป็นโครง Python ส่งให้ GraphBuilderService สร้างกราฟบน Zep และยัดข้อความเข้าไปเป็น “episodes” Zep จะประมวลเป็น GraphRAG (เอนทิตี + เส้นเชื่อม ที่มี “อายุ”/ความถูกต้องตามเวลา)

แปลว่าคุณภาพของทุกอย่างที่ตามมา ขึ้นกับคุณภาพของ seed ที่ป้อน — garbage in, garbage out ในระดับโครงสร้าง

2.2 ขั้น 2 — ปั้นประชากร agent จากกราฟ

OasisProfileGenerator เดินเข้าไปอ่านเอนทิตีในกราฟ แล้วให้ LLM ปั้นแต่ละตัวเป็น OasisAgentProfile — ตัวละครเต็มตัว ไม่ใช่แค่ป้ายชื่อ ฟิลด์จริงในโครงสร้าง:

กลุ่มฟิลด์ฟิลด์ (จาก source)หมายถึง
ตัวตนname · bio · personaคำบรรยายบุคลิก/น้ำเสียงที่ LLM จะสวมตอนแสดง
ประชากรศาสตร์age · gender · mbti · country · professionภูมิหลังที่ทำให้ react ต่างกัน
ความสนใจinterested_topicsหัวข้อที่ตัวนี้จะสนใจ/เข้าไปยุ่ง
น้ำหนักโซเชียลkarma (Reddit) · follower_count (Twitter)สถานะในแพลตฟอร์ม
ที่มาsource_entity_uuid · source_entity_typeโยงกลับไปเอนทิตีต้นทางในกราฟ seed

แต่ละ agent ถูกแปลงเป็นได้ทั้งรูปแบบ Reddit และ Twitter (to_reddit_format / to_twitter_format) เพื่อรันสองแพลตฟอร์มพร้อมกัน

2.3 ขั้น 3 — ตั้งพารามิเตอร์ (คันโยก “พระเจ้า”)

นี่คือส่วนที่สำคัญที่สุดสำหรับงานพี่ SimulationConfigGenerator อ่านโจทย์ภาษาคน (“จำลองว่าหลัง X ความเห็นจะ…”) แล้วสร้าง SimulationParameters ที่มีคันโยกควบคุมฝูงชนละเอียดมาก — และพี่ override เองได้ คันโยกที่ตรงกับ event-driven/activist:

คันโยกฟิลด์ (source)ความหมายใช้กับ activist ยังไง
จุดยืนstancesupportive / opposing / neutral / observerตั้งล่วงหน้าว่ากองไหนหนุน กองไหนค้าน activist
อคติอารมณ์sentiment_bias−1.0 ถึง 1.0ทิศอารมณ์เริ่มต้นของแต่ละผู้เล่น
น้ำหนักอิทธิพลinfluence_weightโอกาสที่เสียงตัวนี้จะถูกคนอื่นเห็นกองทุนใหญ่/ISS ถ่วงน้ำหนักมากกว่า retail
ตัวจุดชนวนinitial_postsโพสต์ตั้งต้นตอนเริ่มจำลอง= deck ของ activist
เหตุการณ์ตามเวลาscheduled_eventsฉีดเหตุการณ์ ณ ชั่วโมงที่กำหนด“ISS แนะให้โหวต FOR” ที่ชม.36 (มุมพระเจ้า)
ห้องเสียงสะท้อนecho_chamber_strengthความรุนแรงของการจับกลุ่มความเห็นเดียวกันความเห็นลามเป็นก้อนเร็วแค่ไหน
เกณฑ์ไวรัลviral_thresholdจำนวน interaction ที่ทำให้กระจายตัวจุด tipping ของการแพร่

ส่วนเวลา (TimeSimulationConfig) ดีฟอลต์จำลอง 72 ชั่วโมง (3 วัน), 1 รอบ = 1 ชม.จำลอง ข้อควรระวัง ตารางจังหวะความ active ถูก hardcode ตาม “นิสัยคนจีน” (พีคช่วงค่ำ 19–22 น., ตี 0–5 แทบตาย) — ดูผลกระทบในข้อ 4

2.4 ขั้น 4 — รันจำลองบน OASIS (สองแพลตฟอร์มขนาน)

SimulationRunner ไม่ได้รันในตัวมันเอง แต่ spawn subprocess ไปรันสคริปต์ใน backend/scripts/ — เลือกได้ว่า run_reddit_simulation.py, run_twitter_simulation.py หรือ run_parallel_simulation.py (รันทั้งคู่พร้อมกัน) สคริปต์เรียก OASIS (oasis.make, generate_reddit_agent_graph) และผูกโมเดลผ่าน CAMEL:

ModelFactory.create(model_platform=ModelPlatformType.OPENAI, model_type=llm_model)

ทุก agent วิ่งผ่าน endpoint แบบ OpenAI โดย override OPENAI_API_BASE_URL = นี่คือเหตุผลที่ เสียบ GLM ได้ทันที (ดูข้อ 5)

แต่ละรอบ agent เลือก “แอ็กชัน” ตามแพลตฟอร์ม:

แพลตฟอร์มแอ็กชันที่ทำได้ (source)
Reddit (13)LIKE_POST · DISLIKE_POST · CREATE_POST · CREATE_COMMENT · LIKE_COMMENT · DISLIKE_COMMENT · SEARCH_POSTS · SEARCH_USER · TREND · REFRESH · FOLLOW · MUTE · DO_NOTHING
Twitter (6)CREATE_POST · LIKE_POST · REPOST · QUOTE_POST · FOLLOW · DO_NOTHING

สองกลไก “มุมพระเจ้า” ระหว่างรัน: (1) scheduled_events ฉีดตามเวลาที่วางไว้ และ (2) SimulationIPC ช่องสื่อสารให้ backend ฉีดคำสั่ง/สัมภาษณ์ agent สด ๆ ระหว่างจำลอง พร้อมกันนั้น ZepGraphMemoryUpdater สตรีมกิจกรรม agent กลับเข้ากราฟเป็น episode ใหม่ตลอดเวลา (ลูกศรประในแผนภาพ) — กราฟจึง “มีชีวิต” วิวัฒน์ตามการจำลอง

2.5 ขั้น 5 — ReportAgent และการคุยกับ agent

ReportAgent เป็น ReAct agent (คิด → เรียกเครื่องมือ → สังเกตผล วนไป) เขียนรายงานทีละหัวข้อ โดยค้นจากกราฟหลังจำลอง (ที่ตอนนี้บรรจุกิจกรรม agent ทั้งหมดแล้ว) มี 4 เครื่องมือ:

เครื่องมือทำอะไร
insight_forgeค้นเชิงลึก — แตกคำถามเป็นหลายมุม รวมผล semantic + เอนทิตี + ความสัมพันธ์
panorama_searchค้นภาพรวม — เห็นเส้นเวลา แยก “ข้อเท็จจริงที่ยัง valid” vs “ที่ล้าสมัย” → ดูว่าความเห็นวิวัฒน์ยังไง
quick_searchค้นเร็ว — ยืนยันข้อเท็จจริงจุดเดียว
interview_agentsสัมภาษณ์ agent จริง ผ่าน OASIS API ทั้งสองแพลตฟอร์ม (ไม่ใช่ LLM ปลอมเสียง) — “นักศึกษาคิดไง สื่อคิดไง ทางการว่าไง”

ขอบเขต (จาก config): สูงสุด 5 tool calls ต่อหัวข้อ, 2 ต่อแชต, temperature 0.5 นอกจากรายงานแล้ว ผู้ใช้ยังเข้าไป “คุยกับ agent ตัวไหนก็ได้” ในโลกจำลองได้โดยตรง

3.2 เคสจำลองสำหรับงานพี่ — activist campaign

เชื่อมกับ Nidec Test

Nidec Test ถามว่าวิกฤตทำลาย ทรัพย์สินจริง (กับดัก) หรือแค่ ชื่อเสียง (โอกาส) ถ้าแค่ชื่อเสียง = perception ต่ำกว่า reality หุ้น mispriced — คำถามถัดมาที่ valuation ตอบไม่ได้คือ “perception จะกลับมาเท่า reality เมื่อไหร่/ยังไง” นั่นคือกระบวนการฝูงชน = กราฟข้างบน MiroFish เติมครึ่งหลังของ Nidec Test ที่งบการเงินมองไม่เห็น

LLM_API_KEY=<z.ai key>

LLM_MODEL_NAME=glm-4.6 # หรือ glm-4.5-air สำหรับ bulk agents

  • ToS GLM Coding Plan จำกัดใช้เฉพาะ coding tools ที่ support เท่านั้น — MiroFish ไม่ใช่ coding tool เอา coding sub มารัน social sim = นอกขอบเขต เสี่ยงโดน ban

  • JSON mode (response_format) ของ chat_json ควร test แยกว่า GLM honor ครบ

สรุป Decision

  • อยากได้ ตัวเลข return → MiroFish ไม่ใช่เครื่องมือ ใช้ myDamo/TBF
  • อยากได้ narrative/sentiment dynamics เป็น input ให้ event-driven thesis → มีศักยภาพจริง แต่ต้องครบ 3 ข้อ: (a) build บน OASIS ไม่ใช่ MiroFish, (b) แก้ cast/time ให้ตรงตลาด, (c) ใช้ general GLM API ไม่ใช่ coding sub
  • use case แรกที่ควรเริ่ม = Japan activist research (fit แรงสุด + มี Nidec Test รองรับ) ทำ P0 backtest fidelity ก่อนเสมอ
  • ถ้าไม่ใช่งาน activist/event-driven → ยังไม่มีโปรเจคไหนคุ้มที่จะแตะ ปล่อยผ่าน
