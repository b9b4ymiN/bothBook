คุณไม่ได้ทดสอบ "ระบบไหนชนะ" — คุณกำลังทดสอบ มิติไหนของการลงทุนที่สำคัญที่สุดในตลาดไทย และนี่คือคำถามที่มี value มากกว่ามาก

เพราะคำตอบของคำถามแรก (winner) จะเปลี่ยนตามตลาดและช่วงเวลา แต่คำตอบของคำถามที่สอง (มิติ) เป็น insight ที่ generalize ได้ในระยะยาว

Greenblatt ในฐานะ Control Benchmark

ผมต้องชม decision นี้ การใช้ Greenblatt เป็น control ไม่ใช่ candidate คือ design ที่ฉลาดมาก เพราะ Magic Formula:

1. ง่ายที่สุดในกลุ่ม — ranking by Earnings Yield + ROC
2. มี peer-reviewed research ระดับโลก — ใน US ทำได้ ~17%/ปี เป็น 20 ปี
3. ถ้า 4 strategies อื่นแพ้ Greenblatt ใน SET → แสดงว่าทุกตัวอ่อน หรือ implementation ผิด
4. ถ้า strategies ชนะ Greenblatt ได้ → แสดงว่าพวกเขามี edge จริง

นี่คือสิ่งที่ Greenblatt เองไม่เคยตั้งใจ — เขาเขียน The Little Book that Beats the Market ในฐานะ user manual แต่ในงานคุณ มันกลายเป็น scientific control variable ที่ standardize การเปรียบเทียบ

Cost Anatomy — แตกตัวเลขให้เห็น

ทำไม cost ถึงกัด CANSLIM แรงกว่า SEPA แม้ trade count ใกล้เคียง (152 vs 86)?

The Math

Round-trip cost ต่อ trade ในตลาดไทย = commission 0.157% × 2 + slippage 0.5-1% × 2 ≈ 1.6-2.3% ต่อ trade

SEPA: 86 trades × ~2% = ~1.7% ต่อปี cost burden (ใน 3 ปี = 5.7% ของ portfolio)

CANSLIM: 152 trades × ~2% = ~3.0% ต่อปี cost burden (ใน 3 ปี = 10.1% ของ portfolio)

Damodaran: 310 trades × ~2.3% = ~7.1% ต่อปี cost burden (ใน 3 ปี = 23.8% ของ portfolio)

นี่คือคำตอบทางคณิตศาสตร์ — Damodaran ไม่ได้แย่เพราะปรัชญาผิด มันแย่เพราะ implementation ของคุณบน SET สร้าง turnover ที่สูงเกินกว่าที่ market microstructure ของไทยจะรับได้

Greenblatt — กรณีพิเศษที่บอกอะไรลึก

สังเกต Greenblatt: cost impact +0.09 จุด — แทบไม่เปลี่ยน นี่ไม่ใช่ความบังเอิญ

หลังจากที่คุณ fix bug stale stop และตั้ง refresh_interval=30 วัน จาก 252 วัน — ระบบกลายเป็น "ถือยาว" และ trade count ลดจาก 428 → 252 ในขณะ baseline (-12.39%) สูงกว่าตัวอื่นมาก costs จึงไม่กัดเพิ่ม

แต่ที่น่าสนใจกว่า — Magic Formula ใน US ทำ ~17%/ปี เป็น 20 ปี ใน SET ทำ -12% ใน 3 ปี นี่บอกอะไร?

A Hard Truth

Systematic strategies ที่ work ใน US ตลาดที่ liquid กว่า, broader, มี longer history — ไม่จำเป็นต้อง work ใน SET

คำว่า "Magic Formula" ใน Thailand context ควรอ่านเป็น "Magic Formula in a Different Context" และต้อง re-prove ทุกข้อสมมติฐาน ก่อนใช้

นี่คือคำเตือนสำหรับใครก็ตามที่อ่านหนังสือ US แล้วคิดว่า "ในไทยก็ใช้ได้เหมือนกัน" — บางทีไม่ใช่

Statistical Caution

4 trades ใน sample ขนาด 12 — ไม่พอจะสรุป statistically significant อะไรได้

SEPA ใน Sideways อาจเป็น artifact ของ data — ไม่ใช่ feature ของระบบ มันโชคดีที่ 1 trade ใน 4 ตัว ทำกำไรเยอะมาก

การเอาผลนี้ไปสรุปว่า "ใช้ SEPA ใน sideways" — เป็นการ overgeneralize จาก data น้อยเกิน

The Lesson

3,067% CAGR ใน 3 ปี เท่ากับเงิน 100k → 33 ล้านบาท ใน 3 ปี ถ้าคุณเชื่อตัวเลขนี้ และเอาเงินจริงไป — คุณจะไม่ได้เริ่มมีพอร์ตเงินจริง คุณจะ blow up ที่ไม้ 2-3

การ ไม่เชื่อตัวเลขที่ดีเกินไป และไล่หา root cause — คือ skill ที่หาเงินซื้อไม่ได้

Column Mismatch — ปัญหาเล็กที่ทำลายโครงการใหญ่

Damodaran, Klarman, CANSLIM ทั้งสามได้ 0 trades ในการ run แรก — เพราะ column name mismatch ระหว่าง snake_case (ที่คุณเขียน) กับ PascalCase (ที่ database เก็บ)

นี่คือ bug ที่ ไม่ส่ง error — แค่ return 0 ผลลัพธ์เงียบๆ ถ้าคุณไม่สังเกต คุณจะนึกว่า "Damodaran ไม่ work บน SET" — และ conclude ผิดทั้งโครงการ

ตัวที่ช่วยให้คุณจับได้คือ Gate Waterfall Diagnostic — log ที่บอกว่า "867 หุ้น → ผ่าน quality gate เหลือ 55 → ผ่าน eps gate เหลือ 0" คุณเห็น "0" ตรงนี้ และคุณ debug ได้

Engineering Wisdom

ระบบที่ดีไม่ใช่ระบบที่ "ไม่มี bug" — ระบบที่ดีคือระบบที่ เปิดเผย bug ของตัวเอง เมื่อมันเกิด

Gate waterfall ของคุณคือ design choice ที่ฉลาด — มันเปลี่ยนปัญหาที่ "ไม่มีใครเห็น" เป็นปัญหา "ที่ทุกคนเห็นทันที"

ในการลงทุนจริง — สิ่งเดียวกันนี้ใช้ได้: ทำให้ "ปัญหา" ของพอร์ตคุณ เห็นได้ก่อนมันโต เช่น เขียน thesis ลงกระดาษ ตั้ง alert เมื่อ position หาย thesis

SEPA Non-determinism — Bug ที่อันตรายที่สุด

16 trades, 33 trades, 86 trades — ขึ้นกับรอบ run นี่คือ bug ที่อันตรายมาก เพราะ:

1. ผลที่ได้ "ดู" ทุกครั้ง — แต่ไม่ตรงกัน
2. ถ้าคุณ run แค่ครั้งเดียวและรายงาน — คุณรายงานสิ่งที่ random
3. นี่คือ form ของ data snooping ที่ง่ายที่สุด — และยากที่สุดที่จะจับ

คุณจับได้เพราะคุณ run ซ้ำหลายครั้ง — และเห็นว่าผลไม่ stable การที่คุณทำเช่นนั้น แสดงว่าคุณมี scientific instinct ที่ดี

ข้อ 5 — 3 ปีไม่พอจะตัดสิน Strategy ใดๆ

Statistics 101: sample size 3 ปีของ regime-imbalanced market = data ไม่พอจะ reject null hypothesis อะไรได้

เพื่อเปรียบเทียบ — papers ที่ peer-reviewed ใน Journal of Finance ที่ test value vs growth strategy ใน developed markets — มักใช้ 30+ ปี ของ data

ข้อ 6 — Implementation Gap ที่ยังไม่มีในงาน

Backtest วัดได้:

✓ Strategy logic
✓ Cost ที่ assumed
✓ Slippage ที่ assumed

Backtest วัดไม่ได้:

✗ Real fill rate (partial fills, order rejection)
✗ Liquidity ที่จริงในวันที่ trade (ไม่ใช่ที่ assumed)
✗ Tax impact (capital gains)
✗ Behavioral cost (คุณกล้ากดตามระบบจริงไหมตอน drawdown -15%?)

The Behavioral Gap

นักวิจัย Andrew Lo (MIT) ประมาณว่า implementation gap ในตลาด emerging market อยู่ที่ 1-3% ต่อปี ขึ้นอยู่กับ strategy

SEPA after-cost ทำ −4.39% — implementation gap อาจเป็น −5.5 ถึง −7.5% ในชีวิตจริง

นี่คือเหตุผลที่ paper trading 6-12 เดือน สำคัญก่อนเอาเงินจริง

ทุกระบบ trade ที่ผ่าน in-sample test ดูดี — เพราะมัน fit กับ data ที่คุณ test ด้วย OOS test คือการถามว่า "ระบบนี้ generalize ไป data ใหม่ ที่ไม่เคยเห็นได้ไหม" และคำตอบ มัก surprise คนที่ไม่ skeptical

กฎ OOS Test ที่คุณเขียนไว้ — และต้องตามทุกข้อ

OOS Validation Protocol
  1. Freeze code ก่อน OOS — ห้ามแตะ strategy logic หลังเริ่ม OOS test มิเช่นนั้นผลที่ได้ไม่ใช่ OOS อีกต่อไป
  2. ใช้ cost model เดียวกัน — Thai friction (commission 0.157% × 2 + slippage 0.5-1%) ห้ามเปลี่ยน
  3. กฎเหล็ก: CAGR drop จาก in-sample > 30% → ระบบ overfitted ห้ามใช้ในชีวิตจริง
  4. กฎทอง: Max DD เพิ่มขึ้น > 50% จาก in-sample → ระบบไม่ robust ต้องทบทวน
  5. Document ทุกผล — แม้จะไม่ผ่าน — เพราะ failure จะสอนคุณมากกว่า success
  6. ห้าม "ครั้งนี้ต่าง" — ถ้าผลไม่ผ่านกฎ ห้ามหา exception ห้าม cherry-pick metric

ที่สำคัญกว่า OOS — Walk-Forward Analysis

OOS test เดียว = single shot ถ้าคุณโชคดี ผลผ่าน ถ้าคุณโชคร้าย ผลแพ้ — แต่คุณตัดสินไม่ได้ว่ามันเป็น signal หรือ noise

Walk-forward analysis คือ rolling validation — train 2 ปี → test 6 เดือน → roll forward → train 2 ปีถัดไป → test 6 เดือนถัดไป — ทำซ้ำหลายๆ window

# Walk-Forward Schema Window 1: Train 2019-01 to 2020-12 Test 2021-01 to 2021-06 Window 2: Train 2019-07 to 2021-06 Test 2021-07 to 2021-12 Window 3: Train 2020-01 to 2021-12 Test 2022-01 to 2022-06 ... Window N: Train 2024-01 to 2025-12 Test 2026-01 to 2026-06 # ผลลัพธ์: ตัวเลขผ่านการ test หลาย rolling window # → ลด luck factor → conviction สูงขึ้นมาก

Marcos López de Prado (Advances in Financial Machine Learning) สอนว่า — single OOS test ให้ false sense of security walk-forward คือ minimum standard ของ rigorous quant research

ถ้าเกิดขึ้น — กฎเหล็กที่ต้องตาม:

Transition Rule

Confirmation signals: (1) SET TRI cross MA200 + breadth, (2) Sector rotation pattern, (3) VIX/sentiment indicator change

Step 4: Position Lifecycle — กฎต่อ Position

ก่อนเข้า:

✓ Regime check ผ่าน — ใช้ system ที่ตรง regime
✓ Stock ผ่าน screen ของ system นั้น (ไม่ผสม)
✓ Position size ตามตาราง regime ข้างบน
✓ เขียน thesis 3 ประโยค + exit conditions ลงกระดาษ
✓ Sector exposure < 30% หลังเข้า

หลังเข้า:

✓ ตรวจสอบ thesis ทุกไตรมาส (อ่านงบ Q ใหม่ vs assumptions)
✓ ถ้า thesis เปลี่ยน — ขายทันที ไม่ว่าราคาจะอยู่ที่ไหน
✓ ถ้า winner วิ่งเป็น 30% ของพอร์ต — let it ride แต่ห้ามเพิ่ม
✓ Regime change = ทบทวนทั้งพอร์ต ไม่ใช่ทบทวนทีละตัว

Step 5: Cost-Aware Trade Budget

จากการค้นพบของคุณ — cost burden ที่ acceptable คือ < 2% ของ portfolio ต่อปี:

Max trades per year = Portfolio Size × 2% / Avg cost per trade เช่น พอร์ต 600k × 2% / (2% × 600k / 100) = 100 trades/ปี max

ถ้าระบบของคุณเรียก trade เกิน 100 ครั้ง/ปี — แสดงว่า cost จะกินกำไร ต้องลด frequency หรือ raise threshold
