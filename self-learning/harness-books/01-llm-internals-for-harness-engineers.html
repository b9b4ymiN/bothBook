LLM Internals ที่จำเป็นต้องรู้สำหรับ Harness Engineer

บทนี้ไม่ได้ต้องการให้คุณจำศัพท์ได้มากขึ้น แต่ต้องการให้คุณเริ่มตัดสินใจเชิงระบบได้แม่นขึ้นเมื่อสร้างหรือรีวิว harness ของจริง.

The Core Idea · แก่นของบท

สิ่งที่บทนี้กำลังเปลี่ยนในวิธีคิดของคุณ

บทนี้ทำให้คุณหยุดมองโมเดลเป็นกล่องดำ และเริ่มมองมันเป็นระบบที่มีข้อจำกัดชัดเจนเรื่อง token, attention, sampling และพฤติกรรมหลัง post-training.

คนจำนวนมากสับสนระหว่างความสามารถของ base model กับพฤติกรรมที่ถูกขัดเกลาหลัง post-training และเลยคาดหวังว่าการเปลี่ยน model รุ่นจะไม่กระทบ workflow เดิม.

การเรียนบทนี้ให้เข้าใจง่ายที่สุดคืออ่านผ่านคำถามสามข้อ: หนึ่ง ปัญหานี้เกิดจาก layer ไหนกันแน่; สอง ถ้าปล่อยไว้จะไหลไปกระทบ reliability, safety, cost หรือ operator experience อย่างไร; และสาม เราจะเก็บหลักฐานอะไรเพื่อพิสูจน์ว่าการออกแบบใหม่ดีกว่าเดิม. ถ้าคุณตอบสามข้อนี้ได้ บทนี้จะไม่เป็นแค่ความรู้ แต่จะกลายเป็นเครื่องมือในการตัดสินใจ.

Harness implication

เอกสารที่ดีสำหรับสายนี้ต้องทำให้ผู้อ่านแปลแนวคิดออกมาเป็น implementation shape ได้. ถ้าบทหนึ่งยังไม่ทำให้คุณเห็นว่าจะไปลงใน code, config, tool boundary, eval หรือ trace ตรงไหน แปลว่าบทยังไม่ลงลึกพอ.

Common confusions ที่ควรเคลียร์ก่อนอ่านต่อ

  • คนจำนวนมากสับสนระหว่างความสามารถของ base model กับพฤติกรรมที่ถูกขัดเกลาหลัง post-training และเลยคาดหวังว่าการเปลี่ยน model รุ่นจะไม่กระทบ workflow เดิม.
  • อย่าปล่อยให้คำว่า model capability กลบคำถามเรื่อง environment design, privilege boundaries และ runtime policy.
  • อย่าตัดสินจากเดโมครั้งเดียว เพราะบทนี้เกี่ยวกับพฤติกรรมที่ต้องเสถียรเมื่อ workload โตขึ้นและเงื่อนไขแย่ลง.
  • อย่าถือว่าการอธิบาย intuition เพียงพอ ถ้ายังไม่มีตัวอย่างว่าระบบจริงจะเปลี่ยนอย่างไรหลังนำแนวคิดนี้ไปใช้.
Anchor artifact · สิ่งที่ควรจับต้องได้

หนึ่ง artifact ที่ช่วยให้บทนี้ไม่ลอย

แทนที่จะปล่อยให้บทนี้อยู่ในระดับคำอธิบายอย่างเดียว ส่วนนี้ตั้งใจให้เป็นตัวอย่าง artifact ที่ผู้อ่านสามารถใช้เป็นแบบฝึกคิดหรือดัดแปลงเข้ากับ capstone ได้ทันที. มันไม่จำเป็นต้องเป็น implementation สุดท้าย แต่ควรพอให้เห็นรูปทรงของการออกแบบจริง.

Artifact นี้ช่วยให้ผู้อ่านเห็นว่า internals ไม่ได้มีไว้เพื่อคุยเก่ง แต่มีไว้เพื่อคุม behavior และ cost ของระบบ.

Topic deep dive · 01

Tokenization — BPE, tiktoken, ทำไม 1 คำไทย ≠ 1 token

หัวข้อนี้สำคัญในบท LLM Internals ที่จำเป็นต้องรู้สำหรับ Harness Engineer เพราะมันบอกว่าทีมกำลังใช้ระบบแบบมีข้อจำกัดที่ชัดเจน หรือยังปล่อยให้โมเดลเดาในพื้นที่ที่ควรถูกออกแบบไว้ล่วงหน้า. บทนี้ทำให้คุณหยุดมองโมเดลเป็นกล่องดำ และเริ่มมองมันเป็นระบบที่มีข้อจำกัดชัดเจนเรื่อง token, attention, sampling และพฤติกรรมหลัง post-training.

ถ้าคุณกำลังสร้างของจริง สิ่งแรกที่ควรถามไม่ใช่แค่ 'Tokenization — BPE, tiktoken, ทำไม 1 คำไทย ≠ 1 token คืออะไร' แต่คือมันควรไปนั่งอยู่ในชั้นไหนของระบบ และควรทิ้งสัญญาณอะไรไว้เมื่อเริ่มล้มเหลว. สำหรับหัวข้อนี้ สัญญาณที่มักโผล่ก่อนคือ schema-valid rate ลดลง, latency โตขึ้น, output drift เมื่อเปลี่ยน model settings.

ทำไมคนจำนวนมากพลาดตรงนี้

คนจำนวนมากสับสนระหว่างความสามารถของ base model กับพฤติกรรมที่ถูกขัดเกลาหลัง post-training และเลยคาดหวังว่าการเปลี่ยน model รุ่นจะไม่กระทบ workflow เดิม.

เมื่อทีมยังไม่แยกเรื่องนี้ออกมาอย่างชัดเจน หัวข้ออย่าง Tokenization — BPE, tiktoken, ทำไม 1 คำไทย ≠ 1 token มักถูกฝังอยู่ใน prompt prose, ความเคยชินของคนใช้เครื่องมือ, หรือการตัดสินใจเฉพาะหน้าของ runtime. ผลคือระบบดูเหมือนทำงานได้ แต่เมื่อ workload โตขึ้น ปัญหาจะโผล่ในรูปของต้นทุนที่พุ่ง คุณภาพที่แกว่ง หรือพฤติกรรมที่อธิบายไม่ได้.

ตัวอย่างในระบบจริง

ตัวอย่างคลาสสิกคือ coding agent ที่เลือก model route ไม่เหมาะ: ใช้ sampling สูงกับงาน tool calling แล้วได้ argument แปลก ๆ หรือใช้ context ยาวเกินโดยไม่ compact จน latency บวมโดยไม่มีคุณค่าจริงเพิ่มขึ้น.

ให้ใช้ภาพนี้เป็นจุดยึดเวลาคุณคิดถึง Tokenization — BPE, tiktoken, ทำไม 1 คำไทย ≠ 1 token: ถ้าคุณยังไม่เห็นว่ามันเปลี่ยน trace, config, schema, memory rule หรือ approval flow ตรงไหน แปลว่าหัวข้อนี้ยังถูกเก็บไว้ในชั้นคำอธิบายมากกว่าชั้น implementation.

สิ่งที่ Harness Engineer ต้องตัดสินใจ

  • หัวข้อนี้ควรถูก encode เป็น artifact แบบใดก่อน: model profile config, token budget worksheet, telemetry field ด้าน token/cost.
  • จุดใดคือ trust boundary หรือ cost boundary ที่หัวข้อนี้กำลังแตะอยู่.
  • ถ้าระบบพังเพราะเรื่องนี้ ทีมจะรู้จากสัญญาณใดก่อน: schema-valid rate ลดลง, latency โตขึ้น, output drift เมื่อเปลี่ยน model settings.
  • อะไรคือ deterministic control ขั้นต่ำที่ควรมี และอะไรคือส่วนที่ปล่อยให้ model reasoning ช่วยตัดสินใจได้.

ตัวอย่างคำถาม review ที่ควรถามใน PR หรือ design doc

  • เราแยก runtime settings ตามชนิดงานหรือยัง หรือยังใช้ค่าเดียวทั้งระบบ
  • เรากำลังพึ่งพาให้โมเดลเดาเรื่อง Tokenization — BPE, tiktoken, ทำไม 1 คำไทย ≠ 1 token มากเกินไปหรือไม่.
  • ข้อมูลหรืออำนาจที่เกี่ยวกับหัวข้อนี้อยู่ใน layer ที่เหมาะสมหรือยัง.
  • ถ้า workload โตขึ้น 10 เท่า หัวข้อนี้จะกลายเป็น bottleneck เรื่องใดก่อน.
  • เรามีหลักฐานใดบ้างที่จะใช้พิสูจน์ว่าการเปลี่ยนแปลงตรงนี้ทำให้ระบบดีขึ้นจริง.

แปลเป็น capstone วันนี้

ใน capstone คุณควรเปลี่ยนบทนี้ให้เป็น model selection note, token budget policy, และ sampling profiles ที่แยกตามชนิดงาน.

ถ้าคุณอ่านบทนี้เพื่อเอาไปใช้จริงทันที ให้เลือกเพียงหนึ่ง artifact ที่เกี่ยวกับ Tokenization — BPE, tiktoken, ทำไม 1 คำไทย ≠ 1 token แล้วลงมือแก้ภายในวันนี้. ความเข้าใจจะเริ่มนิ่งเมื่อมันเปลี่ยนสิ่งที่อยู่ใน repo, dashboard, runtime หรือ review process ของคุณ.

Topic deep dive · 02

Transformer attention — intuition, KV cache, attention pattern

เวลาระบบเริ่มโต หัวข้ออย่าง Transformer attention — intuition, KV cache, attention pattern มักเป็นจุดที่แยกระหว่างเดโมที่ดูฉลาดกับ harness ที่ใช้งานได้จริง. ตัวอย่างคลาสสิกคือ coding agent ที่เลือก model route ไม่เหมาะ: ใช้ sampling สูงกับงาน tool calling แล้วได้ argument แปลก ๆ หรือใช้ context ยาวเกินโดยไม่ compact จน latency บวมโดยไม่มีคุณค่าจริงเพิ่มขึ้น.

ในภาษาของวิศวกร หัวข้อนี้กำลังถามว่าคุณจะย้ายความกำกวมออกจากหัวของโมเดลไปอยู่ใน artifact แบบไหน: context budget table, compaction trigger rules, re-injection policy. ถ้า artifact นี้ยังไม่เกิด ความเสี่ยงจะสะสมแบบเงียบ ๆ จนวันหนึ่งโผล่มาเป็น incident.

ทำไมคนจำนวนมากพลาดตรงนี้

เมื่อทีมยังไม่แยกเรื่องนี้ออกมาอย่างชัดเจน หัวข้ออย่าง Transformer attention — intuition, KV cache, attention pattern มักถูกฝังอยู่ใน prompt prose, ความเคยชินของคนใช้เครื่องมือ, หรือการตัดสินใจเฉพาะหน้าของ runtime. ผลคือระบบดูเหมือนทำงานได้ แต่เมื่อ workload โตขึ้น ปัญหาจะโผล่ในรูปของต้นทุนที่พุ่ง คุณภาพที่แกว่ง หรือพฤติกรรมที่อธิบายไม่ได้.

เมื่อทีมยังไม่แยกเรื่องนี้ออกมาอย่างชัดเจน หัวข้ออย่าง Logprobs — เอาไปใช้ทำ confidence scoring, classifier มักถูกฝังอยู่ใน prompt prose, ความเคยชินของคนใช้เครื่องมือ, หรือการตัดสินใจเฉพาะหน้าของ runtime. ผลคือระบบดูเหมือนทำงานได้ แต่เมื่อ workload โตขึ้น ปัญหาจะโผล่ในรูปของต้นทุนที่พุ่ง คุณภาพที่แกว่ง หรือพฤติกรรมที่อธิบายไม่ได้.

สิ่งที่มักพังก่อนใน production

เมื่อหัวข้อนี้ถูกมองข้าม ระบบมักไม่พังทันทีในเดโม แต่จะเริ่มเผยอาการในรูปของ Logprobs — เอาไปใช้ทำ confidence scoring, classifier ที่แปลผลยากขึ้นเรื่อย ๆ. คนจำนวนมากสับสนระหว่างความสามารถของ base model กับพฤติกรรมที่ถูกขัดเกลาหลัง post-training และเลยคาดหวังว่าการเปลี่ยน model รุ่นจะไม่กระทบ workflow เดิม.

นี่คือเหตุผลที่ Harness Engineer ต้องจับสัญญาณเร็วและ encode บทเรียนกลับเข้า runtime หรือ workflow แทนการปล่อยให้ทีมแก้แบบเฉพาะหน้าไปเรื่อย ๆ.

สิ่งที่ Harness Engineer ต้องตัดสินใจ

  • หัวข้อนี้ควรถูก encode เป็น artifact แบบใดก่อน: model profile config, token budget worksheet, telemetry field ด้าน token/cost.
  • จุดใดคือ trust boundary หรือ cost boundary ที่หัวข้อนี้กำลังแตะอยู่.
  • ถ้าระบบพังเพราะเรื่องนี้ ทีมจะรู้จากสัญญาณใดก่อน: schema-valid rate ลดลง, latency โตขึ้น, output drift เมื่อเปลี่ยน model settings.
  • อะไรคือ deterministic control ขั้นต่ำที่ควรมี และอะไรคือส่วนที่ปล่อยให้ model reasoning ช่วยตัดสินใจได้.

ตัวอย่างคำถาม review ที่ควรถามใน PR หรือ design doc

  • เราแยก runtime settings ตามชนิดงานหรือยัง หรือยังใช้ค่าเดียวทั้งระบบ
  • เรากำลังพึ่งพาให้โมเดลเดาเรื่อง Logprobs — เอาไปใช้ทำ confidence scoring, classifier มากเกินไปหรือไม่.
  • ข้อมูลหรืออำนาจที่เกี่ยวกับหัวข้อนี้อยู่ใน layer ที่เหมาะสมหรือยัง.
  • ถ้า workload โตขึ้น 10 เท่า หัวข้อนี้จะกลายเป็น bottleneck เรื่องใดก่อน.
  • เรามีหลักฐานใดบ้างที่จะใช้พิสูจน์ว่าการเปลี่ยนแปลงตรงนี้ทำให้ระบบดีขึ้นจริง.

ใน capstone คุณควรเปลี่ยนบทนี้ให้เป็น model selection note, token budget policy, และ sampling profiles ที่แยกตามชนิดงาน.

ถ้าคุณอ่านบทนี้เพื่อเอาไปใช้จริงทันที ให้เลือกเพียงหนึ่ง artifact ที่เกี่ยวกับ Logprobs — เอาไปใช้ทำ confidence scoring, classifier แล้วลงมือแก้ภายในวันนี้. ความเข้าใจจะเริ่มนิ่งเมื่อมันเปลี่ยนสิ่งที่อยู่ใน repo, dashboard, runtime หรือ review process ของคุณ.

Tool use / Function calling จาก native model perspective — โมเดลรู้จัก tool ได้อย่างไร

หัวข้อนี้สำคัญในบท LLM Internals ที่จำเป็นต้องรู้สำหรับ Harness Engineer เพราะมันบอกว่าทีมกำลังใช้ระบบแบบมีข้อจำกัดที่ชัดเจน หรือยังปล่อยให้โมเดลเดาในพื้นที่ที่ควรถูกออกแบบไว้ล่วงหน้า. บทนี้ทำให้คุณหยุดมองโมเดลเป็นกล่องดำ และเริ่มมองมันเป็นระบบที่มีข้อจำกัดชัดเจนเรื่อง token, attention, sampling และพฤติกรรมหลัง post-training.

ถ้าคุณกำลังสร้างของจริง สิ่งแรกที่ควรถามไม่ใช่แค่ 'Tool use / Function calling จาก native model perspective — โมเดลรู้จัก tool ได้อย่างไร คืออะไร' แต่คือมันควรไปนั่งอยู่ในชั้นไหนของระบบ และควรทิ้งสัญญาณอะไรไว้เมื่อเริ่มล้มเหลว. สำหรับหัวข้อนี้ สัญญาณที่มักโผล่ก่อนคือ tool misuse, malformed arguments, retries เพิ่ม, output ใหญ่เกิน context.

ตัวอย่างในระบบจริง

ตัวอย่างคลาสสิกคือ coding agent ที่เลือก model route ไม่เหมาะ: ใช้ sampling สูงกับงาน tool calling แล้วได้ argument แปลก ๆ หรือใช้ context ยาวเกินโดยไม่ compact จน latency บวมโดยไม่มีคุณค่าจริงเพิ่มขึ้น.
