บทที่ 18 / Chapter 18

Build Your Own Harness — Capstone Project

บทนี้ไม่ได้ต้องการให้คุณจำศัพท์ได้มากขึ้น แต่ต้องการให้คุณเริ่มตัดสินใจเชิงระบบได้แม่นขึ้นเมื่อสร้างหรือรีวิว harness ของจริง.

The Core Idea · แก่นของบท

สิ่งที่บทนี้กำลังเปลี่ยนในวิธีคิดของคุณ

บทนี้คือจุดที่ความรู้ทั้งหมดต้องกลายเป็นระบบหนึ่งระบบที่คุณสร้าง อธิบาย วัด และนำเสนอได้อย่างซื่อสัตย์ต่อ trade-offs ของมัน.

ความสับสนใหญ่ที่สุดคือพยายามทำ breadth มากกว่า depth จนไม่มีส่วนไหนลึกพอจะเป็น portfolio ที่น่าเชื่อถือได้จริง.

การเรียนบทนี้ให้เข้าใจง่ายที่สุดคืออ่านผ่านคำถามสามข้อ: หนึ่ง ปัญหานี้เกิดจาก layer ไหนกันแน่; สอง ถ้าปล่อยไว้จะไหลไปกระทบ reliability, safety, cost หรือ operator experience อย่างไร; และสาม เราจะเก็บหลักฐานอะไรเพื่อพิสูจน์ว่าการออกแบบใหม่ดีกว่าเดิม. ถ้าคุณตอบสามข้อนี้ได้ บทนี้จะไม่เป็นแค่ความรู้ แต่จะกลายเป็นเครื่องมือในการตัดสินใจ.

Harness implication

เอกสารที่ดีสำหรับสายนี้ต้องทำให้ผู้อ่านแปลแนวคิดออกมาเป็น implementation shape ได้. ถ้าบทหนึ่งยังไม่ทำให้คุณเห็นว่าจะไปลงใน code, config, tool boundary, eval หรือ trace ตรงไหน แปลว่าบทยังไม่ลงลึกพอ.

Common confusions ที่ควรเคลียร์ก่อนอ่านต่อ

  • ความสับสนใหญ่ที่สุดคือพยายามทำ breadth มากกว่า depth จนไม่มีส่วนไหนลึกพอจะเป็น portfolio ที่น่าเชื่อถือได้จริง.
  • อย่าปล่อยให้คำว่า model capability กลบคำถามเรื่อง environment design, privilege boundaries และ runtime policy.
  • อย่าตัดสินจากเดโมครั้งเดียว เพราะบทนี้เกี่ยวกับพฤติกรรมที่ต้องเสถียรเมื่อ workload โตขึ้นและเงื่อนไขแย่ลง.
  • อย่าถือว่าการอธิบาย intuition เพียงพอ ถ้ายังไม่มีตัวอย่างว่าระบบจริงจะเปลี่ยนอย่างไรหลังนำแนวคิดนี้ไปใช้.
Anchor artifact · สิ่งที่ควรจับต้องได้

หนึ่ง artifact ที่ช่วยให้บทนี้ไม่ลอย

แทนที่จะปล่อยให้บทนี้อยู่ในระดับคำอธิบายอย่างเดียว ส่วนนี้ตั้งใจให้เป็นตัวอย่าง artifact ที่ผู้อ่านสามารถใช้เป็นแบบฝึกคิดหรือดัดแปลงเข้ากับ capstone ได้ทันที. มันไม่จำเป็นต้องเป็น implementation สุดท้าย แต่ควรพอให้เห็นรูปทรงของการออกแบบจริง.

Capstone chapter ควรบังคับผู้อ่านให้เห็น milestone และเกณฑ์วัดความดีของผลงาน.

เวลาคุณอ่าน artifact นี้ ให้ถามต่อว่าในระบบของคุณอะไรคือ version ที่เล็กที่สุดของมันที่ควรเกิดขึ้นภายในสัปดาห์นี้. การหาคำตอบข้อนี้ได้คือจุดที่บทเรียนเริ่มเปลี่ยนจาก reading material เป็น engineering momentum.

Topic deep dive · 01

Option A: Domain-specific Coding Harness

หัวข้อนี้สำคัญในบท Build Your Own Harness — Capstone Project เพราะมันบอกว่าทีมกำลังใช้ระบบแบบมีข้อจำกัดที่ชัดเจน หรือยังปล่อยให้โมเดลเดาในพื้นที่ที่ควรถูกออกแบบไว้ล่วงหน้า. บทนี้คือจุดที่ความรู้ทั้งหมดต้องกลายเป็นระบบหนึ่งระบบที่คุณสร้าง อธิบาย วัด และนำเสนอได้อย่างซื่อสัตย์ต่อ trade-offs ของมัน.

ถ้าคุณกำลังสร้างของจริง สิ่งแรกที่ควรถามไม่ใช่แค่ 'Option A: Domain-specific Coding Harness คืออะไร' แต่คือมันควรไปนั่งอยู่ในชั้นไหนของระบบ และควรทิ้งสัญญาณอะไรไว้เมื่อเริ่มล้มเหลว. สำหรับหัวข้อนี้ สัญญาณที่มักโผล่ก่อนคือ scope บวม, deliverables ไม่สมดุล, portfolio เล่า trade-offs ไม่ชัด.

ทำไมคนจำนวนมากพลาดตรงนี้

คนมักเริ่มจาก domain ที่กว้างเกินไป เช่น coding assistant ทั่วไป แทนที่จะเลือก niche ที่พิสูจน์ outcome ได้ลึกกว่า.

เมื่อทีมยังไม่แยกเรื่องนี้ออกมาอย่างชัดเจน หัวข้ออย่าง Option A: Domain-specific Coding Harness มักถูกฝังอยู่ใน prompt prose, ความเคยชินของคนใช้เครื่องมือ, หรือการตัดสินใจเฉพาะหน้าของ runtime. ผลคือระบบดูเหมือนทำงานได้ แต่เมื่อ workload โตขึ้น ปัญหาจะโผล่ในรูปของต้นทุนที่พุ่ง คุณภาพที่แกว่ง หรือพฤติกรรมที่อธิบายไม่ได้.

วิธีเลือกให้ชนะตั้งแต่แรก

แทนที่จะทำ agent เขียนโค้ดได้ทุกอย่าง ลองเลือกปัญหาเฉพาะเช่น Terraform refactor, SQL migration checks หรือ React component generation ที่มี eval surface ชัด.

domain ที่แคบลงไม่ได้ทำให้ผลงานเล็กลง แต่ทำให้คุณเก็บหลักฐานได้ลึกขึ้นและเล่า trade-offs ได้คมขึ้น.

สิ่งที่ Harness Engineer ต้องตัดสินใจ

  • หัวข้อนี้ควรถูก encode เป็น artifact แบบใดก่อน: milestone plan, deliverable checklist, scoring rubric, architecture brief.
  • จุดใดคือ trust boundary หรือ cost boundary ที่หัวข้อนี้กำลังแตะอยู่.
  • ถ้าระบบพังเพราะเรื่องนี้ ทีมจะรู้จากสัญญาณใดก่อน: scope บวม, deliverables ไม่สมดุล, portfolio เล่า trade-offs ไม่ชัด.
  • อะไรคือ deterministic control ขั้นต่ำที่ควรมี และอะไรคือส่วนที่ปล่อยให้ model reasoning ช่วยตัดสินใจได้.

ตัวอย่างคำถาม review ที่ควรถามใน PR หรือ design doc

  • สิ่งที่เลือกทำตอนนี้ทำให้ capstone ลึกขึ้นจริง หรือแค่กว้างขึ้นจนหลักฐานอ่อนลง
  • เรากำลังพึ่งพาให้โมเดลเดาเรื่อง Option A: Domain-specific Coding Harness มากเกินไปหรือไม่.
  • ข้อมูลหรืออำนาจที่เกี่ยวกับหัวข้อนี้อยู่ใน layer ที่เหมาะสมหรือยัง.
  • ถ้า workload โตขึ้น 10 เท่า หัวข้อนี้จะกลายเป็น bottleneck เรื่องใดก่อน.
  • เรามีหลักฐานใดบ้างที่จะใช้พิสูจน์ว่าการเปลี่ยนแปลงตรงนี้ทำให้ระบบดีขึ้นจริง.

แปลเป็น capstone วันนี้

บทนี้ควรลงท้ายที่ source code, architecture doc, eval report, cost report, demo video และ public write-up ที่เล่า failure ได้ด้วย.

เขียน problem statement ของ domain ที่เลือกให้เหลือหนึ่งย่อหน้าที่ชัดเรื่อง user, task และ success metric.

Topic deep dive · 02

Option B: Personal Knowledge Agent

เวลาระบบเริ่มโต หัวข้ออย่าง Option B: Personal Knowledge Agent มักเป็นจุดที่แยกระหว่างเดโมที่ดูฉลาดกับ harness ที่ใช้งานได้จริง. capstone ที่ดีไม่ใช่ระบบที่ทำทุกอย่าง แต่คือระบบที่เลือกชัดว่าจะเก่งเรื่องใดและเก็บหลักฐานรอบด้านพอให้คนอื่นเชื่อว่ามันไม่ใช่เดโมฉาบฉวย.

ในภาษาของวิศวกร หัวข้อนี้กำลังถามว่าคุณจะย้ายความกำกวมออกจากหัวของโมเดลไปอยู่ใน artifact แบบไหน: memory map, consolidation workflow, integration plan. ถ้า artifact นี้ยังไม่เกิด ความเสี่ยงจะสะสมแบบเงียบ ๆ จนวันหนึ่งโผล่มาเป็น incident.

ทำไมคนจำนวนมากพลาดตรงนี้

หลายคนทำ personal knowledge agent เป็นเพียง vector search สวย ๆ โดยไม่มี memory discipline ที่อธิบายได้.

เมื่อทีมยังไม่แยกเรื่องนี้ออกมาอย่างชัดเจน หัวข้ออย่าง Option B: Personal Knowledge Agent มักถูกฝังอยู่ใน prompt prose, ความเคยชินของคนใช้เครื่องมือ, หรือการตัดสินใจเฉพาะหน้าของ runtime. ผลคือระบบดูเหมือนทำงานได้ แต่เมื่อ workload โตขึ้น ปัญหาจะโผล่ในรูปของต้นทุนที่พุ่ง คุณภาพที่แกว่ง หรือพฤติกรรมที่อธิบายไม่ได้.

สิ่งที่ควรชัดตั้งแต่ต้น

ถ้าคุณเลือก Option B ให้ตัดสินก่อนว่าอะไรคือ episodic memory, semantic memory, และ procedural memory ของระบบ ไม่เช่นนั้นทุกอย่างจะไหลไปกองที่ retrieval ชั้นเดียว.

เสน่ห์ของ option นี้อยู่ที่การพิสูจน์ว่าคุณออกแบบความจำแบบ self-healing ได้ ไม่ใช่แค่เก็บเยอะที่สุด.

สิ่งที่ Harness Engineer ต้องตัดสินใจ

  • หัวข้อนี้ควรถูก encode เป็น artifact แบบใดก่อน: memory map, consolidation workflow, integration plan.
  • จุดใดคือ trust boundary หรือ cost boundary ที่หัวข้อนี้กำลังแตะอยู่.
  • ถ้าระบบพังเพราะเรื่องนี้ ทีมจะรู้จากสัญญาณใดก่อน: memory บวม, facts stale, retrieval noise สูง, user trust ลดเพราะระบบจำผิดแบบมั่นใจ.
  • อะไรคือ deterministic control ขั้นต่ำที่ควรมี และอะไรคือส่วนที่ปล่อยให้ model reasoning ช่วยตัดสินใจได้.

ตัวอย่างคำถาม review ที่ควรถามใน PR หรือ design doc

  • ระบบนี้รู้จริงจาก source ไหน และอะไรคือสิ่งที่มันเพียงจำได้จาก hint เก่า ๆ
  • เรากำลังพึ่งพาให้โมเดลเดาเรื่อง Option B: Personal Knowledge Agent มากเกินไปหรือไม่.

  • จุดใดคือ trust boundary หรือ cost boundary ที่หัวข้อนี้กำลังแตะอยู่.

  • อะไรคือ deterministic control ขั้นต่ำที่ควรมี และอะไรคือส่วนที่ปล่อยให้ model reasoning ช่วยตัดสินใจได้.

ตัวอย่างคำถาม review ที่ควรถามใน PR หรือ design doc

  • บทนี้เปลี่ยน component ไหนของ capstone และหลักฐานใดจะบอกว่าการเปลี่ยนนั้นดีขึ้นจริง
  • เรากำลังพึ่งพาให้โมเดลเดาเรื่อง เชื่อมทุกบทเข้ากับระบบเดียว มากเกินไปหรือไม่.
  • ข้อมูลหรืออำนาจที่เกี่ยวกับหัวข้อนี้อยู่ใน layer ที่เหมาะสมหรือยัง.
  • ถ้า workload โตขึ้น 10 เท่า หัวข้อนี้จะกลายเป็น bottleneck เรื่องใดก่อน.
  • เรามีหลักฐานใดบ้างที่จะใช้พิสูจน์ว่าการเปลี่ยนแปลงตรงนี้ทำให้ระบบดีขึ้นจริง.

แปลเป็น capstone วันนี้

บทนี้ควรลงท้ายที่ source code, architecture doc, eval report, cost report, demo video และ public write-up ที่เล่า failure ได้ด้วย.

ทำ mapping sheet ว่าแต่ละบทต้องฝาก artifact อะไรไว้ใน capstone หนึ่งชิ้น.

บทนี้คือจุดที่ความรู้ทั้งหมดต้องกลายเป็นระบบหนึ่งระบบที่คุณสร้าง อธิบาย วัด และนำเสนอได้อย่างซื่อสัตย์ต่อ trade-offs ของมัน.
