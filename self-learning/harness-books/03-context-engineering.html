บทที่ 03 / Chapter 03

Context Engineering

บทนี้ไม่ได้ต้องการให้คุณจำศัพท์ได้มากขึ้น แต่ต้องการให้คุณเริ่มตัดสินใจเชิงระบบได้แม่นขึ้นเมื่อสร้างหรือรีวิว harness ของจริง.

The Core Idea · แก่นของบท

สิ่งที่บทนี้กำลังเปลี่ยนในวิธีคิดของคุณ

บทนี้คือแกนของสาย Harness Engineer เพราะมันสอนให้คุณบริหารพื้นที่รับรู้ของโมเดลอย่างจงใจ แทนการโยนทุกอย่างเข้า context แล้วค่อยหวังว่าจะไม่พัง.

หลายคนคิดว่า context ใหญ่ขึ้นคือประกันว่าคุณภาพดีขึ้น แต่ในงานจริง signal-to-noise ratio และ placement ของข้อมูลสำคัญต่างหากที่ชี้ขาด.

การเรียนบทนี้ให้เข้าใจง่ายที่สุดคืออ่านผ่านคำถามสามข้อ: หนึ่ง ปัญหานี้เกิดจาก layer ไหนกันแน่; สอง ถ้าปล่อยไว้จะไหลไปกระทบ reliability, safety, cost หรือ operator experience อย่างไร; และสาม เราจะเก็บหลักฐานอะไรเพื่อพิสูจน์ว่าการออกแบบใหม่ดีกว่าเดิม. ถ้าคุณตอบสามข้อนี้ได้ บทนี้จะไม่เป็นแค่ความรู้ แต่จะกลายเป็นเครื่องมือในการตัดสินใจ.

Harness implication

เอกสารที่ดีสำหรับสายนี้ต้องทำให้ผู้อ่านแปลแนวคิดออกมาเป็น implementation shape ได้. ถ้าบทหนึ่งยังไม่ทำให้คุณเห็นว่าจะไปลงใน code, config, tool boundary, eval หรือ trace ตรงไหน แปลว่าบทยังไม่ลงลึกพอ.

Common confusions ที่ควรเคลียร์ก่อนอ่านต่อ

  • หลายคนคิดว่า context ใหญ่ขึ้นคือประกันว่าคุณภาพดีขึ้น แต่ในงานจริง signal-to-noise ratio และ placement ของข้อมูลสำคัญต่างหากที่ชี้ขาด.
  • อย่าปล่อยให้คำว่า model capability กลบคำถามเรื่อง environment design, privilege boundaries และ runtime policy.
  • อย่าตัดสินจากเดโมครั้งเดียว เพราะบทนี้เกี่ยวกับพฤติกรรมที่ต้องเสถียรเมื่อ workload โตขึ้นและเงื่อนไขแย่ลง.
  • อย่าถือว่าการอธิบาย intuition เพียงพอ ถ้ายังไม่มีตัวอย่างว่าระบบจริงจะเปลี่ยนอย่างไรหลังนำแนวคิดนี้ไปใช้.
Anchor artifact · สิ่งที่ควรจับต้องได้

หนึ่ง artifact ที่ช่วยให้บทนี้ไม่ลอย

แทนที่จะปล่อยให้บทนี้อยู่ในระดับคำอธิบายอย่างเดียว ส่วนนี้ตั้งใจให้เป็นตัวอย่าง artifact ที่ผู้อ่านสามารถใช้เป็นแบบฝึกคิดหรือดัดแปลงเข้ากับ capstone ได้ทันที. มันไม่จำเป็นต้องเป็น implementation สุดท้าย แต่ควรพอให้เห็นรูปทรงของการออกแบบจริง.

Context engineering จะเริ่มจับต้องได้เมื่อคุณเห็น layout ของ token budget อย่าง explicit.

เวลาคุณอ่าน artifact นี้ ให้ถามต่อว่าในระบบของคุณอะไรคือ version ที่เล็กที่สุดของมันที่ควรเกิดขึ้นภายในสัปดาห์นี้. การหาคำตอบข้อนี้ได้คือจุดที่บทเรียนเริ่มเปลี่ยนจาก reading material เป็น engineering momentum.

Topic deep dive · 01

Context window เป็น scarce resource — คิดเหมือน CPU cache ไม่ใช่ disk

หัวข้อนี้สำคัญในบท Context Engineering เพราะมันบอกว่าทีมกำลังใช้ระบบแบบมีข้อจำกัดที่ชัดเจน หรือยังปล่อยให้โมเดลเดาในพื้นที่ที่ควรถูกออกแบบไว้ล่วงหน้า. บทนี้คือแกนของสาย Harness Engineer เพราะมันสอนให้คุณบริหารพื้นที่รับรู้ของโมเดลอย่างจงใจ แทนการโยนทุกอย่างเข้า context แล้วค่อยหวังว่าจะไม่พัง.

ถ้าคุณกำลังสร้างของจริง สิ่งแรกที่ควรถามไม่ใช่แค่ 'Context window เป็น scarce resource — คิดเหมือน CPU cache ไม่ใช่ disk คืออะไร' แต่คือมันควรไปนั่งอยู่ในชั้นไหนของระบบ และควรทิ้งสัญญาณอะไรไว้เมื่อเริ่มล้มเหลว. สำหรับหัวข้อนี้ สัญญาณที่มักโผล่ก่อนคือ prefix ยาวขึ้นแต่คำตอบไม่ดีขึ้น, latency โต, session สับสนเร็วขึ้น.

ทำไมคนจำนวนมากพลาดตรงนี้

คนมักเก็บ history และ tool outputs ทั้งหมดไว้เพราะกลัวลืม จนสุดท้ายโมเดลเห็นทุกอย่างแต่แยกสิ่งสำคัญไม่ออก.

เมื่อทีมยังไม่แยกเรื่องนี้ออกมาอย่างชัดเจน หัวข้ออย่าง Context window เป็น scarce resource — คิดเหมือน CPU cache ไม่ใช่ disk มักถูกฝังอยู่ใน prompt prose, ความเคยชินของคนใช้เครื่องมือ, หรือการตัดสินใจเฉพาะหน้าของ runtime. ผลคือระบบดูเหมือนทำงานได้ แต่เมื่อ workload โตขึ้น ปัญหาจะโผล่ในรูปของต้นทุนที่พุ่ง คุณภาพที่แกว่ง หรือพฤติกรรมที่อธิบายไม่ได้.

ภาพที่ควรนึกให้ออก

นึกถึง coding agent ที่เปิดไฟล์หลายชุด รัน tests หลายรอบ และเก็บ logs ทุกอย่างไว้ใน context เดียวกัน. ตอนต้น session มันดูฉลาด แต่พอผ่านไปสักพักคุณภาพเริ่มตกทั้งที่ข้อมูลมีมากขึ้น.

สาเหตุไม่ใช่ว่ามันโง่ลง แต่เป็นเพราะคุณบังคับให้ attention budget ถูกแชร์กับสิ่งที่หมดประโยชน์ไปแล้ว.

สิ่งที่ Harness Engineer ต้องตัดสินใจ

  • หัวข้อนี้ควรถูก encode เป็น artifact แบบใดก่อน: context budget ledger + eviction policy.
  • จุดใดคือ trust boundary หรือ cost boundary ที่หัวข้อนี้กำลังแตะอยู่.
  • ถ้าระบบพังเพราะเรื่องนี้ ทีมจะรู้จากสัญญาณใดก่อน: prefix ยาวขึ้นแต่คำตอบไม่ดีขึ้น, latency โต, session สับสนเร็วขึ้น.
  • อะไรคือ deterministic control ขั้นต่ำที่ควรมี และอะไรคือส่วนที่ปล่อยให้ model reasoning ช่วยตัดสินใจได้.

ตัวอย่างคำถาม review ที่ควรถามใน PR หรือ design doc

  • ข้อมูลชิ้นนี้จำเป็นต้องอยู่หน้าตาโมเดลตอนนี้จริงหรือแค่รู้สึกเสียดายถ้าเอาออก
  • เรากำลังพึ่งพาให้โมเดลเดาเรื่อง Context window เป็น scarce resource — คิดเหมือน CPU cache ไม่ใช่ disk มากเกินไปหรือไม่.
  • ข้อมูลหรืออำนาจที่เกี่ยวกับหัวข้อนี้อยู่ใน layer ที่เหมาะสมหรือยัง.
  • ถ้า workload โตขึ้น 10 เท่า หัวข้อนี้จะกลายเป็น bottleneck เรื่องใดก่อน.
  • เรามีหลักฐานใดบ้างที่จะใช้พิสูจน์ว่าการเปลี่ยนแปลงตรงนี้ทำให้ระบบดีขึ้นจริง.

แปลเป็น capstone วันนี้

ใน capstone บทนี้ควรเปลี่ยนเป็น context budget table, trigger rules สำหรับ compaction และ policy ว่าอะไรอยู่ in-context อะไรอยู่ external memory.

วาด context layout ปัจจุบันของระบบคุณหนึ่งครั้งแล้ววงส่วนที่เป็น stale-but-still-present ออกมา.

Context budget allocation — system, history, tool defs, output

เวลาระบบเริ่มโต หัวข้ออย่าง Context budget allocation — system, history, tool defs, output มักเป็นจุดที่แยกระหว่างเดโมที่ดูฉลาดกับ harness ที่ใช้งานได้จริง. นึกถึง coding session ที่กินเวลาหลายชั่วโมง มี tool definitions, file snippets, plan state, memory notes และ test logs แข่งกันแย่งพื้นที่ในหน้าต่างเดียวกัน ถ้าไม่มี layout ที่ดี agent จะเริ่มสับสนก่อนที่คุณจะรู้ตัว.

ในภาษาของวิศวกร หัวข้อนี้กำลังถามว่าคุณจะย้ายความกำกวมออกจากหัวของโมเดลไปอยู่ใน artifact แบบไหน: allocation table ต่อ workflow. ถ้า artifact นี้ยังไม่เกิด ความเสี่ยงจะสะสมแบบเงียบ ๆ จนวันหนึ่งโผล่มาเป็น incident.

หลายทีมคิดเรื่อง token budget เฉพาะตอน request เริ่ม fail แล้ว ทั้งที่มันควรถูกออกแบบตั้งแต่ shape ของ prompt.

เมื่อทีมยังไม่แยกเรื่องนี้ออกมาอย่างชัดเจน หัวข้ออย่าง Context budget allocation — system, history, tool defs, output มักถูกฝังอยู่ใน prompt prose, ความเคยชินของคนใช้เครื่องมือ, หรือการตัดสินใจเฉพาะหน้าของ runtime. ผลคือระบบดูเหมือนทำงานได้ แต่เมื่อ workload โตขึ้น ปัญหาจะโผล่ในรูปของต้นทุนที่พุ่ง คุณภาพที่แกว่ง หรือพฤติกรรมที่อธิบายไม่ได้.

workflow วิเคราะห์ incident อาจต้องกัน budget ให้ system rules, current hypothesis, recent traces, และ output summary ไม่เท่ากัน. ถ้าคุณไม่กันส่วนหนึ่งไว้ให้ output โมเดลจะตอบครึ่งเดียวแล้วตาย.

Lost in the middle problem

ให้มอง Lost in the middle problem เป็นการบังคับให้ทีมตัดสินใจในเรื่องที่มักถูกผลักทิ้งไว้ท้ายสุด ไม่ว่าจะเป็น boundary, budget, review surface หรือ recovery path. หลายคนคิดว่า context ใหญ่ขึ้นคือประกันว่าคุณภาพดีขึ้น แต่ในงานจริง signal-to-noise ratio และ placement ของข้อมูลสำคัญต่างหากที่ชี้ขาด.

ความต่างของทีมที่อ่านหัวข้อนี้แล้วได้ผลกับทีมที่อ่านแล้วไม่ได้ผล อยู่ที่การกล้าแปลมันเป็นกติกาที่ตรวจได้. สำหรับหัวข้อนี้ คำถามที่ช่วยมากที่สุดคือ: fact สำคัญของเราถูกวางไว้ใกล้ decision point หรือถูกฝังอยู่กลาง context ยาว ๆ

Just-in-time context loading

หัวข้อนี้สำคัญในบท Context Engineering เพราะมันบอกว่าทีมกำลังใช้ระบบแบบมีข้อจำกัดที่ชัดเจน หรือยังปล่อยให้โมเดลเดาในพื้นที่ที่ควรถูกออกแบบไว้ล่วงหน้า. บทนี้คือแกนของสาย Harness Engineer เพราะมันสอนให้คุณบริหารพื้นที่รับรู้ของโมเดลอย่างจงใจ แทนการโยนทุกอย่างเข้า context แล้วค่อยหวังว่าจะไม่พัง.

ถ้าคุณกำลังสร้างของจริง สิ่งแรกที่ควรถามไม่ใช่แค่ 'Just-in-time context loading คืออะไร' แต่คือมันควรไปนั่งอยู่ในชั้นไหนของระบบ และควรทิ้งสัญญาณอะไรไว้เมื่อเริ่มล้มเหลว. สำหรับหัวข้อนี้ สัญญาณที่มักโผล่ก่อนคือ prefix static ใหญ่เกินจำเป็น, ค่าใช้จ่ายสูงก่อนงานจริงเริ่ม, โมเดลใช้ tool ผิดเพราะเห็นมากเกินไป.

  • หัวข้อนี้ควรถูก encode เป็น artifact แบบใดก่อน: cache key design note.
  • จุดใดคือ trust boundary หรือ cost boundary ที่หัวข้อนี้กำลังแตะอยู่.
  • ถ้าระบบพังเพราะเรื่องนี้ ทีมจะรู้จากสัญญาณใดก่อน: static prefix ถูกจ่ายซ้ำ, latency สูงทั้งที่งานคล้ายเดิม, cache hit rate ต่ำกว่าที่ควร.
  • อะไรคือ deterministic control ขั้นต่ำที่ควรมี และอะไรคือส่วนที่ปล่อยให้ model reasoning ช่วยตัดสินใจได้.

ตัวอย่างคำถาม review ที่ควรถามใน PR หรือ design doc

  • ส่วนไหนของ prompt immutable พอจะ cache ได้จริง และเงื่อนไข invalidation คืออะไร
  • เรากำลังพึ่งพาให้โมเดลเดาเรื่อง Caching — prompt caching, KV cache มากเกินไปหรือไม่.
  • ข้อมูลหรืออำนาจที่เกี่ยวกับหัวข้อนี้อยู่ใน layer ที่เหมาะสมหรือยัง.
  • ถ้า workload โตขึ้น 10 เท่า หัวข้อนี้จะกลายเป็น bottleneck เรื่องใดก่อน.
  • เรามีหลักฐานใดบ้างที่จะใช้พิสูจน์ว่าการเปลี่ยนแปลงตรงนี้ทำให้ระบบดีขึ้นจริง.

แปลเป็น capstone วันนี้

ใน capstone บทนี้ควรเปลี่ยนเป็น context budget table, trigger rules สำหรับ compaction และ policy ว่าอะไรอยู่ in-context อะไรอยู่ external memory.

แยก prompt ของระบบคุณเป็น static prefix กับ dynamic payload ให้ชัดในเอกสารสักหนึ่ง workflow.

Topic deep dive · 07

Anti-distillation และการ design context ให้ทนต่อ extraction

หัวข้อนี้สำคัญในบท Context Engineering เพราะมันบอกว่าทีมกำลังใช้ระบบแบบมีข้อจำกัดที่ชัดเจน หรือยังปล่อยให้โมเดลเดาในพื้นที่ที่ควรถูกออกแบบไว้ล่วงหน้า. บทนี้คือแกนของสาย Harness Engineer เพราะมันสอนให้คุณบริหารพื้นที่รับรู้ของโมเดลอย่างจงใจ แทนการโยนทุกอย่างเข้า context แล้วค่อยหวังว่าจะไม่พัง.

ถ้าคุณกำลังสร้างของจริง สิ่งแรกที่ควรถามไม่ใช่แค่ 'Anti-distillation และการ design context ให้ทนต่อ extraction คืออะไร' แต่คือมันควรไปนั่งอยู่ในชั้นไหนของระบบ และควรทิ้งสัญญาณอะไรไว้เมื่อเริ่มล้มเหลว. สำหรับหัวข้อนี้ สัญญาณที่มักโผล่ก่อนคือ policy blocks ยาวเกิน, internal heuristics ถูกเผยเกินจำเป็น, output สะท้อน hidden scaffolding ตรงเกินไป.

ทำไมคนจำนวนมากพลาดตรงนี้

คนมักคิดเรื่อง anti-distillation เป็นเรื่องขั้นสูงเกินไป ทั้งที่หลักง่ายที่สุดคืออย่า inject สิ่งที่ไม่จำเป็นต่อการตัดสินใจรอบนี้.

เมื่อทีมยังไม่แยกเรื่องนี้ออกมาอย่างชัดเจน หัวข้ออย่าง Anti-distillation และการ design context ให้ทนต่อ extraction มักถูกฝังอยู่ใน prompt prose, ความเคยชินของคนใช้เครื่องมือ, หรือการตัดสินใจเฉพาะหน้าของ runtime. ผลคือระบบดูเหมือนทำงานได้ แต่เมื่อ workload โตขึ้น ปัญหาจะโผล่ในรูปของต้นทุนที่พุ่ง คุณภาพที่แกว่ง หรือพฤติกรรมที่อธิบายไม่ได้.

วิธีใช้กับงานจริง

ถ้า runtime มี internal rules จำนวนมาก คุณอาจย้ายบางส่วนไปอยู่ deterministic guard นอก context แทนการบอกโมเดลหมดทุกข้อทุกครั้ง.

การป้องกัน extraction ที่ดีที่สุดมักเริ่มจาก context hygiene ไม่ใช่จากคำขู่ใน prompt.
