Evaluation-Driven Development

บทนี้ไม่ได้ต้องการให้คุณจำศัพท์ได้มากขึ้น แต่ต้องการให้คุณเริ่มตัดสินใจเชิงระบบได้แม่นขึ้นเมื่อสร้างหรือรีวิว harness ของจริง.

The Core Idea · แก่นของบท

สิ่งที่บทนี้กำลังเปลี่ยนในวิธีคิดของคุณ

บทนี้เปลี่ยนการพัฒนา agent จากการชิม output ด้วยตา ไปสู่การตัดสินด้วยพฤติกรรมที่วัดซ้ำได้และรองรับ regression.

คนมักมอง eval เป็นเฟสท้ายของโปรเจค ทั้งที่ในระบบ agent มันคือวิธีคิดตั้งแต่เริ่มออกแบบ feature.

การเรียนบทนี้ให้เข้าใจง่ายที่สุดคืออ่านผ่านคำถามสามข้อ: หนึ่ง ปัญหานี้เกิดจาก layer ไหนกันแน่; สอง ถ้าปล่อยไว้จะไหลไปกระทบ reliability, safety, cost หรือ operator experience อย่างไร; และสาม เราจะเก็บหลักฐานอะไรเพื่อพิสูจน์ว่าการออกแบบใหม่ดีกว่าเดิม. ถ้าคุณตอบสามข้อนี้ได้ บทนี้จะไม่เป็นแค่ความรู้ แต่จะกลายเป็นเครื่องมือในการตัดสินใจ.

Harness implication

เอกสารที่ดีสำหรับสายนี้ต้องทำให้ผู้อ่านแปลแนวคิดออกมาเป็น implementation shape ได้. ถ้าบทหนึ่งยังไม่ทำให้คุณเห็นว่าจะไปลงใน code, config, tool boundary, eval หรือ trace ตรงไหน แปลว่าบทยังไม่ลงลึกพอ.

Common confusions ที่ควรเคลียร์ก่อนอ่านต่อ

  • คนมักมอง eval เป็นเฟสท้ายของโปรเจค ทั้งที่ในระบบ agent มันคือวิธีคิดตั้งแต่เริ่มออกแบบ feature.
  • อย่าปล่อยให้คำว่า model capability กลบคำถามเรื่อง environment design, privilege boundaries และ runtime policy.
  • อย่าตัดสินจากเดโมครั้งเดียว เพราะบทนี้เกี่ยวกับพฤติกรรมที่ต้องเสถียรเมื่อ workload โตขึ้นและเงื่อนไขแย่ลง.
  • อย่าถือว่าการอธิบาย intuition เพียงพอ ถ้ายังไม่มีตัวอย่างว่าระบบจริงจะเปลี่ยนอย่างไรหลังนำแนวคิดนี้ไปใช้.
Anchor artifact · สิ่งที่ควรจับต้องได้

หนึ่ง artifact ที่ช่วยให้บทนี้ไม่ลอย

แทนที่จะปล่อยให้บทนี้อยู่ในระดับคำอธิบายอย่างเดียว ส่วนนี้ตั้งใจให้เป็นตัวอย่าง artifact ที่ผู้อ่านสามารถใช้เป็นแบบฝึกคิดหรือดัดแปลงเข้ากับ capstone ได้ทันที. มันไม่จำเป็นต้องเป็น implementation สุดท้าย แต่ควรพอให้เห็นรูปทรงของการออกแบบจริง.

บท eval จะชัดขึ้นทันทีเมื่อมีตัวอย่าง rubric และ dataset row.

dataset_row:
  input: "refactor config loader safely"
  expected_behavior:
    - uses file-reading tools before editing
    - avoids shell unless needed
    - returns diff summary

grading:
  deterministic:
    - schema_valid
    - forbidden_tool_not_used
  judge:
    - plan quality 1-5
    - faithfulness 1-5

เวลาคุณอ่าน artifact นี้ ให้ถามต่อว่าในระบบของคุณอะไรคือ version ที่เล็กที่สุดของมันที่ควรเกิดขึ้นภายในสัปดาห์นี้. การหาคำตอบข้อนี้ได้คือจุดที่บทเรียนเริ่มเปลี่ยนจาก reading material เป็น engineering momentum.

Topic deep dive · 01

ทำไม eval ของ agent ≠ unit test ปกติ

หัวข้อนี้สำคัญในบท Evaluation-Driven Development เพราะมันบอกว่าทีมกำลังใช้ระบบแบบมีข้อจำกัดที่ชัดเจน หรือยังปล่อยให้โมเดลเดาในพื้นที่ที่ควรถูกออกแบบไว้ล่วงหน้า. บทนี้เปลี่ยนการพัฒนา agent จากการชิม output ด้วยตา ไปสู่การตัดสินด้วยพฤติกรรมที่วัดซ้ำได้และรองรับ regression.

ถ้าคุณกำลังสร้างของจริง สิ่งแรกที่ควรถามไม่ใช่แค่ 'ทำไม eval ของ agent ≠ unit test ปกติ คืออะไร' แต่คือมันควรไปนั่งอยู่ในชั้นไหนของระบบ และควรทิ้งสัญญาณอะไรไว้เมื่อเริ่มล้มเหลว. สำหรับหัวข้อนี้ สัญญาณที่มักโผล่ก่อนคือ ทีมเถียงกันจากตัวอย่างเฉพาะหน้า, regression หลุด, compare รุ่นใหม่ไม่ได้.

ทำไมคนจำนวนมากพลาดตรงนี้

คนมักมอง eval เป็นเฟสท้ายของโปรเจค ทั้งที่ในระบบ agent มันคือวิธีคิดตั้งแต่เริ่มออกแบบ feature.

เมื่อทีมยังไม่แยกเรื่องนี้ออกมาอย่างชัดเจน หัวข้ออย่าง ทำไม eval ของ agent ≠ unit test ปกติ มักถูกฝังอยู่ใน prompt prose, ความเคยชินของคนใช้เครื่องมือ, หรือการตัดสินใจเฉพาะหน้าของ runtime. ผลคือระบบดูเหมือนทำงานได้ แต่เมื่อ workload โตขึ้น ปัญหาจะโผล่ในรูปของต้นทุนที่พุ่ง คุณภาพที่แกว่ง หรือพฤติกรรมที่อธิบายไม่ได้.

ตัวอย่างในระบบจริง

หากคุณกำลังสร้าง coding harness แล้วปรับ prompt ทุกวันโดยไม่มี eval suite คุณจะตอบไม่ได้เลยว่ารุ่นเมื่อวานหรือวันนี้ปลอดภัยกว่าและสำเร็จงานดีกว่ากันจริงหรือไม่.

ให้ใช้ภาพนี้เป็นจุดยึดเวลาคุณคิดถึง ทำไม eval ของ agent ≠ unit test ปกติ: ถ้าคุณยังไม่เห็นว่ามันเปลี่ยน trace, config, schema, memory rule หรือ approval flow ตรงไหน แปลว่าหัวข้อนี้ยังถูกเก็บไว้ในชั้นคำอธิบายมากกว่าชั้น implementation.

สิ่งที่ Harness Engineer ต้องตัดสินใจ

  • หัวข้อนี้ควรถูก encode เป็น artifact แบบใดก่อน: eval rubric, dataset slice, CI gate, failure taxonomy.
  • จุดใดคือ trust boundary หรือ cost boundary ที่หัวข้อนี้กำลังแตะอยู่.
  • ถ้าระบบพังเพราะเรื่องนี้ ทีมจะรู้จากสัญญาณใดก่อน: ทีมเถียงกันจากตัวอย่างเฉพาะหน้า, regression หลุด, compare รุ่นใหม่ไม่ได้.
  • อะไรคือ deterministic control ขั้นต่ำที่ควรมี และอะไรคือส่วนที่ปล่อยให้ model reasoning ช่วยตัดสินใจได้.

ตัวอย่างคำถาม review ที่ควรถามใน PR หรือ design doc

  • เรากำลังวัด behavior ที่ผู้ใช้แคร์จริงหรือเพียงวัดสิ่งที่ตรวจง่าย
  • เรากำลังพึ่งพาให้โมเดลเดาเรื่อง ทำไม eval ของ agent ≠ unit test ปกติ มากเกินไปหรือไม่.
  • ข้อมูลหรืออำนาจที่เกี่ยวกับหัวข้อนี้อยู่ใน layer ที่เหมาะสมหรือยัง.
  • ถ้า workload โตขึ้น 10 เท่า หัวข้อนี้จะกลายเป็น bottleneck เรื่องใดก่อน.
  • เรามีหลักฐานใดบ้างที่จะใช้พิสูจน์ว่าการเปลี่ยนแปลงตรงนี้ทำให้ระบบดีขึ้นจริง.

ถ้าคุณอ่านบทนี้เพื่อเอาไปใช้จริงทันที ให้เลือกเพียงหนึ่ง artifact ที่เกี่ยวกับ ทำไม eval ของ agent ≠ unit test ปกติ แล้วลงมือแก้ภายในวันนี้. ความเข้าใจจะเริ่มนิ่งเมื่อมันเปลี่ยนสิ่งที่อยู่ใน repo, dashboard, runtime หรือ review process ของคุณ.

วิธีคิดแบบ reviewer นี้ทำให้ Behavior-driven eval — eval ตาม user-facing behavior กลายเป็นเครื่องมือในการตั้งคำถามที่ดีขึ้น ไม่ใช่แค่เนื้อหาสำหรับจดจำ.

สิ่งที่ Harness Engineer ต้องตัดสินใจ

  • หัวข้อนี้ควรถูก encode เป็น artifact แบบใดก่อน: eval rubric, dataset slice, CI gate, failure taxonomy.
  • จุดใดคือ trust boundary หรือ cost boundary ที่หัวข้อนี้กำลังแตะอยู่.
  • ถ้าระบบพังเพราะเรื่องนี้ ทีมจะรู้จากสัญญาณใดก่อน: ทีมเถียงกันจากตัวอย่างเฉพาะหน้า, regression หลุด, compare รุ่นใหม่ไม่ได้.
  • อะไรคือ deterministic control ขั้นต่ำที่ควรมี และอะไรคือส่วนที่ปล่อยให้ model reasoning ช่วยตัดสินใจได้.

ตัวอย่างคำถาม review ที่ควรถามใน PR หรือ design doc

  • เรากำลังวัด behavior ที่ผู้ใช้แคร์จริงหรือเพียงวัดสิ่งที่ตรวจง่าย
  • เรากำลังพึ่งพาให้โมเดลเดาเรื่อง Behavior-driven eval — eval ตาม user-facing behavior มากเกินไปหรือไม่.
  • ข้อมูลหรืออำนาจที่เกี่ยวกับหัวข้อนี้อยู่ใน layer ที่เหมาะสมหรือยัง.
  • ถ้า workload โตขึ้น 10 เท่า หัวข้อนี้จะกลายเป็น bottleneck เรื่องใดก่อน.
  • เรามีหลักฐานใดบ้างที่จะใช้พิสูจน์ว่าการเปลี่ยนแปลงตรงนี้ทำให้ระบบดีขึ้นจริง.

แปลเป็น capstone วันนี้

บทนี้ควรกลายเป็น dataset slices, judge policy, deterministic assertions และ regression dashboard ของคุณ.

ถ้าคุณอ่านบทนี้เพื่อเอาไปใช้จริงทันที ให้เลือกเพียงหนึ่ง artifact ที่เกี่ยวกับ Behavior-driven eval — eval ตาม user-facing behavior แล้วลงมือแก้ภายในวันนี้. ความเข้าใจจะเริ่มนิ่งเมื่อมันเปลี่ยนสิ่งที่อยู่ใน repo, dashboard, runtime หรือ review process ของคุณ.

บทนี้เปลี่ยนการพัฒนา agent จากการชิม output ด้วยตา ไปสู่การตัดสินด้วยพฤติกรรมที่วัดซ้ำได้และรองรับ regression.
