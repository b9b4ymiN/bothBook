The Core Idea · แก่นของบท

สิ่งที่บทนี้กำลังเปลี่ยนในวิธีคิดของคุณ

บทนี้ย้ำว่าทุกครั้งที่ agent มีอำนาจเพิ่ม คุณกำลังสร้าง security boundary ใหม่ และต้องคิดเรื่อง blast radius ควบคู่กับ convenience เสมอ.

หลายทีมหวังให้ allowlist ยาว ๆ แก้ทุกอย่าง แต่พอ command ดูปลอดภัยในชื่อ กลับอันตรายที่ arguments หรือ composition กับ tool อื่น.

การเรียนบทนี้ให้เข้าใจง่ายที่สุดคืออ่านผ่านคำถามสามข้อ: หนึ่ง ปัญหานี้เกิดจาก layer ไหนกันแน่; สอง ถ้าปล่อยไว้จะไหลไปกระทบ reliability, safety, cost หรือ operator experience อย่างไร; และสาม เราจะเก็บหลักฐานอะไรเพื่อพิสูจน์ว่าการออกแบบใหม่ดีกว่าเดิม. ถ้าคุณตอบสามข้อนี้ได้ บทนี้จะไม่เป็นแค่ความรู้ แต่จะกลายเป็นเครื่องมือในการตัดสินใจ.

Harness implication

เอกสารที่ดีสำหรับสายนี้ต้องทำให้ผู้อ่านแปลแนวคิดออกมาเป็น implementation shape ได้. ถ้าบทหนึ่งยังไม่ทำให้คุณเห็นว่าจะไปลงใน code, config, tool boundary, eval หรือ trace ตรงไหน แปลว่าบทยังไม่ลงลึกพอ.

Common confusions ที่ควรเคลียร์ก่อนอ่านต่อ

  • หลายทีมหวังให้ allowlist ยาว ๆ แก้ทุกอย่าง แต่พอ command ดูปลอดภัยในชื่อ กลับอันตรายที่ arguments หรือ composition กับ tool อื่น.
  • อย่าปล่อยให้คำว่า model capability กลบคำถามเรื่อง environment design, privilege boundaries และ runtime policy.
  • อย่าตัดสินจากเดโมครั้งเดียว เพราะบทนี้เกี่ยวกับพฤติกรรมที่ต้องเสถียรเมื่อ workload โตขึ้นและเงื่อนไขแย่ลง.
  • อย่าถือว่าการอธิบาย intuition เพียงพอ ถ้ายังไม่มีตัวอย่างว่าระบบจริงจะเปลี่ยนอย่างไรหลังนำแนวคิดนี้ไปใช้.

ให้มอง Dangerous flags — --yolo, --accept-all เป็นการบังคับให้ทีมตัดสินใจในเรื่องที่มักถูกผลักทิ้งไว้ท้ายสุด ไม่ว่าจะเป็น boundary, budget, review surface หรือ recovery path. หลายทีมหวังให้ allowlist ยาว ๆ แก้ทุกอย่าง แต่พอ command ดูปลอดภัยในชื่อ กลับอันตรายที่ arguments หรือ composition กับ tool อื่น.

ความต่างของทีมที่อ่านหัวข้อนี้แล้วได้ผลกับทีมที่อ่านแล้วไม่ได้ผล อยู่ที่การกล้าแปลมันเป็นกติกาที่ตรวจได้. สำหรับหัวข้อนี้ คำถามที่ช่วยมากที่สุดคือ: เหตุผลทางผลิตภัณฑ์ของการมี flag นี้แข็งแรงพอจะรับความเสี่ยงที่มันเปิดหรือยัง

ทำไมคนจำนวนมากพลาดตรงนี้

ทีมมักเก็บ --yolo ไว้เพื่อเดโมหรือ power users แล้วลืมว่ามันค่อย ๆ กลายเป็นทางลัดประจำวันของคนในทีมเอง.

เมื่อทีมยังไม่แยกเรื่องนี้ออกมาอย่างชัดเจน หัวข้ออย่าง Dangerous flags — --yolo, --accept-all มักถูกฝังอยู่ใน prompt prose, ความเคยชินของคนใช้เครื่องมือ, หรือการตัดสินใจเฉพาะหน้าของ runtime. ผลคือระบบดูเหมือนทำงานได้ แต่เมื่อ workload โตขึ้น ปัญหาจะโผล่ในรูปของต้นทุนที่พุ่ง คุณภาพที่แกว่ง หรือพฤติกรรมที่อธิบายไม่ได้.

ตัวอย่างที่ควรกลัวให้ถูกจุด

ถ้าโหมดรับทุกคำสั่งถูกเปิดพร้อม shell access และ network access ผู้ใช้ไม่ได้แค่ประหยัดคลิก แต่กำลังข้ามชั้นป้องกันหลายชั้นพร้อมกัน.

ธงอันตรายจึงต้องมีทั้ง copy ที่เตือนชัด, telemetry แยก, และ policy ว่าเมื่อไรบ้างที่ห้ามเปิดโดยเด็ดขาด.

สิ่งที่ Harness Engineer ต้องตัดสินใจ

  • หัวข้อนี้ควรถูก encode เป็น artifact แบบใดก่อน: dangerous-mode policy + explicit warning copy.
  • จุดใดคือ trust boundary หรือ cost boundary ที่หัวข้อนี้กำลังแตะอยู่.
  • ถ้าระบบพังเพราะเรื่องนี้ ทีมจะรู้จากสัญญาณใดก่อน: ระบบ fail-open, approvals ถูกข้ามจนกลายเป็นนิสัย, destructive action เกิดได้จากคลิกเดียว.
  • อะไรคือ deterministic control ขั้นต่ำที่ควรมี และอะไรคือส่วนที่ปล่อยให้ model reasoning ช่วยตัดสินใจได้.

ตัวอย่างคำถาม review ที่ควรถามใน PR หรือ design doc

  • เหตุผลทางผลิตภัณฑ์ของการมี flag นี้แข็งแรงพอจะรับความเสี่ยงที่มันเปิดหรือยัง
  • เรากำลังพึ่งพาให้โมเดลเดาเรื่อง Dangerous flags — --yolo, --accept-all มากเกินไปหรือไม่.

ถ้าคุณกำลังสร้างของจริง สิ่งแรกที่ควรถามไม่ใช่แค่ 'Human-in-the-loop checkpoints คืออะไร' แต่คือมันควรไปนั่งอยู่ในชั้นไหนของระบบ และควรทิ้งสัญญาณอะไรไว้เมื่อเริ่มล้มเหลว. สำหรับหัวข้อนี้ สัญญาณที่มักโผล่ก่อนคือ approval fatigue, ผู้ใช้กดผ่านแบบไม่อ่าน, หรือกลับกันคือระบบถามจนงานไหลไม่ออก.

Anti-distillation เป็นเคสพิเศษของ security

หัวข้อนี้สำคัญในบท Permission, Sandboxing & Security เพราะมันบอกว่าทีมกำลังใช้ระบบแบบมีข้อจำกัดที่ชัดเจน หรือยังปล่อยให้โมเดลเดาในพื้นที่ที่ควรถูกออกแบบไว้ล่วงหน้า. บทนี้ย้ำว่าทุกครั้งที่ agent มีอำนาจเพิ่ม คุณกำลังสร้าง security boundary ใหม่ และต้องคิดเรื่อง blast radius ควบคู่กับ convenience เสมอ.

ถ้าคุณกำลังสร้างของจริง สิ่งแรกที่ควรถามไม่ใช่แค่ 'Anti-distillation เป็นเคสพิเศษของ security คืออะไร' แต่คือมันควรไปนั่งอยู่ในชั้นไหนของระบบ และควรทิ้งสัญญาณอะไรไว้เมื่อเริ่มล้มเหลว. สำหรับหัวข้อนี้ สัญญาณที่มักโผล่ก่อนคือ unsafe command attempts, approval churn, privilege escalation risk, hidden exfiltration paths.

ทำไมคนจำนวนมากพลาดตรงนี้

หลายทีมหวังให้ allowlist ยาว ๆ แก้ทุกอย่าง แต่พอ command ดูปลอดภัยในชื่อ กลับอันตรายที่ arguments หรือ composition กับ tool อื่น.

เมื่อทีมยังไม่แยกเรื่องนี้ออกมาอย่างชัดเจน หัวข้ออย่าง Anti-distillation เป็นเคสพิเศษของ security มักถูกฝังอยู่ใน prompt prose, ความเคยชินของคนใช้เครื่องมือ, หรือการตัดสินใจเฉพาะหน้าของ runtime. ผลคือระบบดูเหมือนทำงานได้ แต่เมื่อ workload โตขึ้น ปัญหาจะโผล่ในรูปของต้นทุนที่พุ่ง คุณภาพที่แกว่ง หรือพฤติกรรมที่อธิบายไม่ได้.

ตัวอย่างในระบบจริง

ลองนึกถึง bash tool ที่มี access ถึง repo, network และ secrets พร้อมกัน. ถ้า approval surface กับ sandbox ไม่ชัด คุณกำลังสร้าง backdoor ที่สุภาพมากกว่าสร้างผู้ช่วยวิศวกร.

ให้ใช้ภาพนี้เป็นจุดยึดเวลาคุณคิดถึง Anti-distillation เป็นเคสพิเศษของ security: ถ้าคุณยังไม่เห็นว่ามันเปลี่ยน trace, config, schema, memory rule หรือ approval flow ตรงไหน แปลว่าหัวข้อนี้ยังถูกเก็บไว้ในชั้นคำอธิบายมากกว่าชั้น implementation.
