The Core Idea · แก่นของบท

สิ่งที่บทนี้กำลังเปลี่ยนในวิธีคิดของคุณ

บทนี้สอนให้คุณรักข้อจำกัดของ token budget แทนการใช้โมเดลแพงสุดทุกครั้ง เพราะระบบจะ scale ได้จริงก็ต่อเมื่อ economics และ latency อยู่ในระดับที่ยอมรับได้.

ความเข้าใจผิดหลักคือคิดว่าการลด cost ต้องแลกกับคุณภาพเสมอ ทั้งที่หลายครั้งลดได้จาก prompt shape, caching และ loop discipline โดยแทบไม่เสีย outcome.

การเรียนบทนี้ให้เข้าใจง่ายที่สุดคืออ่านผ่านคำถามสามข้อ: หนึ่ง ปัญหานี้เกิดจาก layer ไหนกันแน่; สอง ถ้าปล่อยไว้จะไหลไปกระทบ reliability, safety, cost หรือ operator experience อย่างไร; และสาม เราจะเก็บหลักฐานอะไรเพื่อพิสูจน์ว่าการออกแบบใหม่ดีกว่าเดิม. ถ้าคุณตอบสามข้อนี้ได้ บทนี้จะไม่เป็นแค่ความรู้ แต่จะกลายเป็นเครื่องมือในการตัดสินใจ.

Harness implication

เอกสารที่ดีสำหรับสายนี้ต้องทำให้ผู้อ่านแปลแนวคิดออกมาเป็น implementation shape ได้. ถ้าบทหนึ่งยังไม่ทำให้คุณเห็นว่าจะไปลงใน code, config, tool boundary, eval หรือ trace ตรงไหน แปลว่าบทยังไม่ลงลึกพอ.

  • อย่าปล่อยให้คำว่า model capability กลบคำถามเรื่อง environment design, privilege boundaries และ runtime policy.

  • อย่าถือว่าการอธิบาย intuition เพียงพอ ถ้ายังไม่มีตัวอย่างว่าระบบจริงจะเปลี่ยนอย่างไรหลังนำแนวคิดนี้ไปใช้.

ความเข้าใจผิดหลักคือคิดว่าการลด cost ต้องแลกกับคุณภาพเสมอ ทั้งที่หลายครั้งลดได้จาก prompt shape, caching และ loop discipline โดยแทบไม่เสีย outcome.

เมื่อทีมยังไม่แยกเรื่องนี้ออกมาอย่างชัดเจน หัวข้ออย่าง Compute-time vs accuracy tradeoff มักถูกฝังอยู่ใน prompt prose, ความเคยชินของคนใช้เครื่องมือ, หรือการตัดสินใจเฉพาะหน้าของ runtime. ผลคือระบบดูเหมือนทำงานได้ แต่เมื่อ workload โตขึ้น ปัญหาจะโผล่ในรูปของต้นทุนที่พุ่ง คุณภาพที่แกว่ง หรือพฤติกรรมที่อธิบายไม่ได้.

มุมมองแบบผู้รีวิวระบบ

เวลาอ่านหัวข้อนี้ ให้ลองสมมติว่าคุณเป็น reviewer ที่ต้องอนุมัติ design ของทีม. คุณจะไม่ถามแค่ว่าเข้าใจคำศัพท์นี้ไหม แต่จะถามว่า boundary ถูกวางไว้ถูกชั้นหรือยัง และ evidence ที่จะพิสูจน์การตัดสินใจนี้อยู่ตรงไหน.

วิธีคิดแบบ reviewer นี้ทำให้ Compute-time vs accuracy tradeoff กลายเป็นเครื่องมือในการตั้งคำถามที่ดีขึ้น ไม่ใช่แค่เนื้อหาสำหรับจดจำ.

สิ่งที่ Harness Engineer ต้องตัดสินใจ

  • หัวข้อนี้ควรถูก encode เป็น artifact แบบใดก่อน: design note, checklist, metric, หรือ policy ที่ตรวจได้จริง.
  • จุดใดคือ trust boundary หรือ cost boundary ที่หัวข้อนี้กำลังแตะอยู่.
  • ถ้าระบบพังเพราะเรื่องนี้ ทีมจะรู้จากสัญญาณใดก่อน: คุณภาพแกว่ง, การตัดสินใจอธิบายยาก, ทีมต้องแก้ด้วยมือบ่อย.
  • อะไรคือ deterministic control ขั้นต่ำที่ควรมี และอะไรคือส่วนที่ปล่อยให้ model reasoning ช่วยตัดสินใจได้.

ตัวอย่างคำถาม review ที่ควรถามใน PR หรือ design doc

  • ถ้าถอดหัวข้อนี้ออกจากระบบวันนี้ จุดไหนจะเริ่มพังก่อน
  • เรากำลังพึ่งพาให้โมเดลเดาเรื่อง Compute-time vs accuracy tradeoff มากเกินไปหรือไม่.
  • ข้อมูลหรืออำนาจที่เกี่ยวกับหัวข้อนี้อยู่ใน layer ที่เหมาะสมหรือยัง.
  • ถ้า workload โตขึ้น 10 เท่า หัวข้อนี้จะกลายเป็น bottleneck เรื่องใดก่อน.
  • เรามีหลักฐานใดบ้างที่จะใช้พิสูจน์ว่าการเปลี่ยนแปลงตรงนี้ทำให้ระบบดีขึ้นจริง.

แปลเป็น capstone วันนี้

เปลี่ยนบทนี้เป็น route policy, cache plan, cost ledger, latency waterfall และ budget alerts.

ถ้าคุณอ่านบทนี้เพื่อเอาไปใช้จริงทันที ให้เลือกเพียงหนึ่ง artifact ที่เกี่ยวกับ Compute-time vs accuracy tradeoff แล้วลงมือแก้ภายในวันนี้. ความเข้าใจจะเริ่มนิ่งเมื่อมันเปลี่ยนสิ่งที่อยู่ใน repo, dashboard, runtime หรือ review process ของคุณ.

บทนี้สอนให้คุณรักข้อจำกัดของ token budget แทนการใช้โมเดลแพงสุดทุกครั้ง เพราะระบบจะ scale ได้จริงก็ต่อเมื่อ economics และ latency อยู่ในระดับที่ยอมรับได้.
