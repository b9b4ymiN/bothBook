Tool / Function Calling Design

บทนี้ไม่ได้ต้องการให้คุณจำศัพท์ได้มากขึ้น แต่ต้องการให้คุณเริ่มตัดสินใจเชิงระบบได้แม่นขึ้นเมื่อสร้างหรือรีวิว harness ของจริง.

The Core Idea · แก่นของบท

สิ่งที่บทนี้กำลังเปลี่ยนในวิธีคิดของคุณ

บทนี้เปลี่ยนวิธีคิดจากมอง tool เป็น feature ไปสู่การมอง tool เป็น interface contract ที่มี privilege, context cost และ failure mode ของตัวเอง.

หลายทีมออกแบบ tool จากมุมคนเขียน runtime ล้วน ๆ จนลืมว่าคนใช้จริงคือโมเดล ซึ่งต้องการ semantic boundary ที่ชัดมากกว่าชื่อฟังก์ชันเท่ ๆ.

การเรียนบทนี้ให้เข้าใจง่ายที่สุดคืออ่านผ่านคำถามสามข้อ: หนึ่ง ปัญหานี้เกิดจาก layer ไหนกันแน่; สอง ถ้าปล่อยไว้จะไหลไปกระทบ reliability, safety, cost หรือ operator experience อย่างไร; และสาม เราจะเก็บหลักฐานอะไรเพื่อพิสูจน์ว่าการออกแบบใหม่ดีกว่าเดิม. ถ้าคุณตอบสามข้อนี้ได้ บทนี้จะไม่เป็นแค่ความรู้ แต่จะกลายเป็นเครื่องมือในการตัดสินใจ.

Harness implication

เอกสารที่ดีสำหรับสายนี้ต้องทำให้ผู้อ่านแปลแนวคิดออกมาเป็น implementation shape ได้. ถ้าบทหนึ่งยังไม่ทำให้คุณเห็นว่าจะไปลงใน code, config, tool boundary, eval หรือ trace ตรงไหน แปลว่าบทยังไม่ลงลึกพอ.

Common confusions ที่ควรเคลียร์ก่อนอ่านต่อ

  • หลายทีมออกแบบ tool จากมุมคนเขียน runtime ล้วน ๆ จนลืมว่าคนใช้จริงคือโมเดล ซึ่งต้องการ semantic boundary ที่ชัดมากกว่าชื่อฟังก์ชันเท่ ๆ.
  • อย่าปล่อยให้คำว่า model capability กลบคำถามเรื่อง environment design, privilege boundaries และ runtime policy.
  • อย่าตัดสินจากเดโมครั้งเดียว เพราะบทนี้เกี่ยวกับพฤติกรรมที่ต้องเสถียรเมื่อ workload โตขึ้นและเงื่อนไขแย่ลง.
  • อย่าถือว่าการอธิบาย intuition เพียงพอ ถ้ายังไม่มีตัวอย่างว่าระบบจริงจะเปลี่ยนอย่างไรหลังนำแนวคิดนี้ไปใช้.
Anchor artifact · สิ่งที่ควรจับต้องได้

หนึ่ง artifact ที่ช่วยให้บทนี้ไม่ลอย

แทนที่จะปล่อยให้บทนี้อยู่ในระดับคำอธิบายอย่างเดียว ส่วนนี้ตั้งใจให้เป็นตัวอย่าง artifact ที่ผู้อ่านสามารถใช้เป็นแบบฝึกคิดหรือดัดแปลงเข้ากับ capstone ได้ทันที. มันไม่จำเป็นต้องเป็น implementation สุดท้าย แต่ควรพอให้เห็นรูปทรงของการออกแบบจริง.

บทนี้ควรมีภาพของ tool contract ที่ดีอย่างน้อยหนึ่งชิ้นให้ผู้อ่านเลียนแบบได้.

{
  "name": "read_file_segment",
  "description": "Use when you need exact file contents for reasoning. Avoid for shell execution or broad repo search.",
  "input_schema": {
    "type": "object",
    "properties": {
      "path": {"type": "string"},
      "start_line": {"type": "integer", "minimum": 1},
      "end_line": {"type": "integer", "minimum": 1}
    },
    "required": ["path"],
    "additionalProperties": false
  },
  "permission_tier": "read-only"
}

เวลาคุณอ่าน artifact นี้ ให้ถามต่อว่าในระบบของคุณอะไรคือ version ที่เล็กที่สุดของมันที่ควรเกิดขึ้นภายในสัปดาห์นี้. การหาคำตอบข้อนี้ได้คือจุดที่บทเรียนเริ่มเปลี่ยนจาก reading material เป็น engineering momentum.

Anti-pattern: tool ที่โมเดลใช้ผิดทาง

ให้มอง Anti-pattern: tool ที่โมเดลใช้ผิดทาง เป็นการบังคับให้ทีมตัดสินใจในเรื่องที่มักถูกผลักทิ้งไว้ท้ายสุด ไม่ว่าจะเป็น boundary, budget, review surface หรือ recovery path. หลายทีมออกแบบ tool จากมุมคนเขียน runtime ล้วน ๆ จนลืมว่าคนใช้จริงคือโมเดล ซึ่งต้องการ semantic boundary ที่ชัดมากกว่าชื่อฟังก์ชันเท่ ๆ.

ความต่างของทีมที่อ่านหัวข้อนี้แล้วได้ผลกับทีมที่อ่านแล้วไม่ได้ผล อยู่ที่การกล้าแปลมันเป็นกติกาที่ตรวจได้. สำหรับหัวข้อนี้ คำถามที่ช่วยมากที่สุดคือ: ชื่อและ description ของ interface นี้บอกโมเดลชัดพอหรือยังว่าควรใช้เมื่อไรและไม่ควรใช้เมื่อไร

หลายทีมออกแบบ tool จากมุมคนเขียน runtime ล้วน ๆ จนลืมว่าคนใช้จริงคือโมเดล ซึ่งต้องการ semantic boundary ที่ชัดมากกว่าชื่อฟังก์ชันเท่ ๆ.

เมื่อทีมยังไม่แยกเรื่องนี้ออกมาอย่างชัดเจน หัวข้ออย่าง Anti-pattern: tool ที่โมเดลใช้ผิดทาง มักถูกฝังอยู่ใน prompt prose, ความเคยชินของคนใช้เครื่องมือ, หรือการตัดสินใจเฉพาะหน้าของ runtime. ผลคือระบบดูเหมือนทำงานได้ แต่เมื่อ workload โตขึ้น ปัญหาจะโผล่ในรูปของต้นทุนที่พุ่ง คุณภาพที่แกว่ง หรือพฤติกรรมที่อธิบายไม่ได้.

มุมมองแบบผู้รีวิวระบบ

เวลาอ่านหัวข้อนี้ ให้ลองสมมติว่าคุณเป็น reviewer ที่ต้องอนุมัติ design ของทีม. คุณจะไม่ถามแค่ว่าเข้าใจคำศัพท์นี้ไหม แต่จะถามว่า boundary ถูกวางไว้ถูกชั้นหรือยัง และ evidence ที่จะพิสูจน์การตัดสินใจนี้อยู่ตรงไหน.

วิธีคิดแบบ reviewer นี้ทำให้ Anti-pattern: tool ที่โมเดลใช้ผิดทาง กลายเป็นเครื่องมือในการตั้งคำถามที่ดีขึ้น ไม่ใช่แค่เนื้อหาสำหรับจดจำ.

สิ่งที่ Harness Engineer ต้องตัดสินใจ

  • หัวข้อนี้ควรถูก encode เป็น artifact แบบใดก่อน: JSON schema, tool registry, permission metadata, concise/raw result modes.
  • จุดใดคือ trust boundary หรือ cost boundary ที่หัวข้อนี้กำลังแตะอยู่.
  • ถ้าระบบพังเพราะเรื่องนี้ ทีมจะรู้จากสัญญาณใดก่อน: tool misuse, malformed arguments, retries เพิ่ม, output ใหญ่เกิน context.
  • อะไรคือ deterministic control ขั้นต่ำที่ควรมี และอะไรคือส่วนที่ปล่อยให้ model reasoning ช่วยตัดสินใจได้.

ตัวอย่างคำถาม review ที่ควรถามใน PR หรือ design doc

  • ชื่อและ description ของ interface นี้บอกโมเดลชัดพอหรือยังว่าควรใช้เมื่อไรและไม่ควรใช้เมื่อไร
  • เรากำลังพึ่งพาให้โมเดลเดาเรื่อง Anti-pattern: tool ที่โมเดลใช้ผิดทาง มากเกินไปหรือไม่.
  • ข้อมูลหรืออำนาจที่เกี่ยวกับหัวข้อนี้อยู่ใน layer ที่เหมาะสมหรือยัง.
  • ถ้า workload โตขึ้น 10 เท่า หัวข้อนี้จะกลายเป็น bottleneck เรื่องใดก่อน.
  • เรามีหลักฐานใดบ้างที่จะใช้พิสูจน์ว่าการเปลี่ยนแปลงตรงนี้ทำให้ระบบดีขึ้นจริง.

แปลเป็น capstone วันนี้

เปลี่ยนบทนี้เป็น tool registry พร้อม schema tests, permission metadata และ result shaping modes ที่มี concise/raw ชัดเจน.

ถ้าคุณอ่านบทนี้เพื่อเอาไปใช้จริงทันที ให้เลือกเพียงหนึ่ง artifact ที่เกี่ยวกับ Anti-pattern: tool ที่โมเดลใช้ผิดทาง แล้วลงมือแก้ภายในวันนี้. ความเข้าใจจะเริ่มนิ่งเมื่อมันเปลี่ยนสิ่งที่อยู่ใน repo, dashboard, runtime หรือ review process ของคุณ.

บทนี้เปลี่ยนวิธีคิดจากมอง tool เป็น feature ไปสู่การมอง tool เป็น interface contract ที่มี privilege, context cost และ failure mode ของตัวเอง.
