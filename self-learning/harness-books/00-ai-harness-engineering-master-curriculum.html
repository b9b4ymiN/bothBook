Foreword · คำจาก mentor

หลักสูตรนี้ไม่ได้สอนให้คุณเก่ง prompt อย่างเดียว

Harness Engineer คือคนที่ยืนอยู่ตรงจุดเชื่อมระหว่าง model behavior กับ production discipline. เขาต้องคิดเรื่อง tools, loops, memory, safety, cost, observability, build pipeline และ operator experience พร้อมกัน. นั่นคือเหตุผลที่หลักสูตรนี้ต้องถูกอ่านแบบระบบ ไม่ใช่แบบเก็บศัพท์ทีละคำ.

ถ้าคุณเป็น Software Developer ที่ใช้ AI APIs ได้อยู่แล้ว จุดเปลี่ยนสำคัญไม่ใช่การรู้จัก framework ใหม่เพิ่มอีกตัว แต่คือการเริ่มมองว่าปัญหาไหนควรแก้ที่ prompt, ปัญหาไหนควรแก้ที่ context, ปัญหาไหนควรแก้ที่ tool boundary, และปัญหาไหนควรแก้ที่ eval หรือ policy layer. หลักสูตรนี้ถูกสร้างมาเพื่อฝึกสายตาแบบนั้น.

หมายเหตุด้าน curriculum contract: ชุดเอกสารนี้ยึดโครง 6 Part / 18 บทจากบทความอ้างอิงที่ผู้ใช้ส่งมาเป็น canonical delivery spine สำหรับงานนี้ จึงอาจไม่ตรง 1:1 กับ backbone เริ่มต้นของ repo เดิมในบางจุดลำดับ.

Roadmap · วิธีเดิน

วิธีใช้หลักสูตรนี้ให้ได้ผลจริง

เดือนแรกควรเลือก capstone หนึ่งอันก่อน แล้วใช้ทุกบทเป็นแรงกดให้ capstone โตขึ้นอย่างมีชั้นเชิง. ถ้าไม่มีระบบจริงให้ผูก เนื้อหาจำนวนมากจะกลายเป็นความรู้ที่จำได้แต่ตัดสินใจไม่เป็น. ในทางกลับกัน ถ้าคุณมี capstone ตั้งแต่แรก บทต่าง ๆ จะกลายเป็น decision material ทันที.

ลำดับการอ่านที่แนะนำสำหรับคนมีพื้นฐาน SWE + AI อยู่แล้วคือเริ่มจาก Context Engineering เพื่อเห็นแก่นของข้อจำกัดก่อน แล้วค่อยย้อนอ่าน LLM internals กับ Prompt Engineering อย่างเป็นระบบ. หลังจากนั้นให้เดินตามโครงของหลักสูตรเพื่อไม่ให้วิ่งไป multi-agent หรือ MCP ก่อนจะมีรากเรื่อง tool, loop และ memory ที่แน่นพอ.

Roadmap 6 เดือน

  • เดือน 1 — Part 1 + project เล็กคู่ขนาน
  • เดือน 2 — Part 2 + เริ่ม capstone scaffolding
  • เดือน 3 — Part 3 + integrate เข้ากับ capstone
  • เดือน 4 — Part 4 + harden capstone
  • เดือน 5 — Part 5 + finalize และเขียน blog
  • เดือน 6 — polish capstone + apply jobs / open-source contribution

Checklist ความพร้อม

  • อธิบายความต่างของ prompt engineering, context engineering, harness engineering ได้
  • เขียน MCP server ที่ผ่าน security review ได้
  • ออกแบบ 3-layer memory ของ agent ใหม่ได้ตั้งแต่ศูนย์
  • รู้ว่าเมื่อไหร่ไม่ควร multi-agent
  • เขียน eval ก่อนเขียน feature ได้เป็นนิสัย
  • อธิบาย compaction strategies ของ Claude Code ได้
  • ตอบได้ว่า cost ของ harness ตัวเองเป็นเท่าไหร่ต่อ task
  • อ่าน source code ของ Aider/Cline/Continue ได้ใน 2 ชั่วโมง
  • ออกแบบ permission system ที่ context-aware ได้
  • มี capstone project ใน GitHub พร้อม eval report และ architecture doc

Chapter 01
LLM Internals ที่จำเป็นต้องรู้สำหรับ Harness Engineer

Part: Part 1 · Foundations — รู้จักโมเดลและบริบทอย่างแท้จริง

Why this chapter exists: บทนี้ปู mental model ให้คุณอธิบายได้ว่าทำไม context ยาวขึ้นแล้วช้าลง ทำไม tool calling เปราะเมื่อ sampling สูงเกินไป และทำไม hallucination ไม่ใช่บั๊กที่แก้ด้วย prompt อย่างเดียว.

Mentor lens: บทนี้ทำให้คุณหยุดมองโมเดลเป็นกล่องดำ และเริ่มมองมันเป็นระบบที่มีข้อจำกัดชัดเจนเรื่อง token, attention, sampling และพฤติกรรมหลัง post-training.

Capstone translation: ใน capstone คุณควรเปลี่ยนบทนี้ให้เป็น model selection note, token budget policy, และ sampling profiles ที่แยกตามชนิดงาน.

เรื่องที่ต้องเรียน

  • Tokenization — BPE, tiktoken, ทำไม 1 คำไทย ≠ 1 token
  • Transformer attention — intuition, KV cache, attention pattern
  • Context window จริงๆ คืออะไร — physical limit, ทำไมยิ่งใหญ่ยิ่งช้าและแพง
  • Sampling parameters — temperature, top_p, top_k และผลต่อ tool calling reliability
  • Logprobs — เอาไปใช้ทำ confidence scoring, classifier
  • Pre-training vs Post-training (RLHF, DPO) — ส่งผลต่อ behavior อย่างไร

What the learner should be able to do

  • อ่าน release note ของโมเดลใหม่แล้วแปลผลต่อระบบได้
  • ตอบได้ว่าทำไมโมเดลลืมเมื่อ context ยาว
  • เลือก sampling profile ให้เหมาะกับงานได้
Chapter 02
Prompt Engineering ระดับ Production

Part: Part 1 · Foundations — รู้จักโมเดลและบริบทอย่างแท้จริง

Why this chapter exists: ใน harness จริง prompt ถูกเรียกใช้ซ้ำจำนวนมหาศาล ความคลุมเครือเล็กน้อยจึงแปลเป็นค่าใช้จ่าย ความไม่สม่ำเสมอ และ incident ได้ทันที.

Mentor lens: บทนี้สอนให้คุณมอง prompt เป็น policy artifact ที่ต้อง review, test, version และ rollback ได้ ไม่ใช่ข้อความยาว ๆ ที่ฝากไว้ในโค้ดแล้วหวังว่าทุกอย่างจะดีเอง.

Capstone translation: เปลี่ยนบทนี้ให้กลายเป็น prompt registry, prompt review checklist และ regression eval สำหรับ prompts สำคัญ.

เรื่องที่ต้องเรียน

  • Anatomy of a system prompt — role, instructions, examples, constraints, output format
  • Few-shot vs zero-shot และเมื่อไหร่ few-shot ทำให้แย่ลง
  • Chain-of-Thought / Reasoning prompts — extended thinking, scratchpad
  • Structured output — JSON mode, schema enforcement
  • Negative instructions — ทำไมการบอกอย่าทำ X ได้ผลน้อยกว่า ทำ Y แทน
  • Prompt injection และวิธีป้องกันเชิงสถาปัตยกรรม

What the learner should be able to do

  • เขียน system prompt ที่เสถียรพอสำหรับ production
  • ออกแบบ prompt ให้ทนต่อ input แบบ adversarial
  • รู้ว่าจุดไหนควรหยุดแก้ด้วย prompt แล้วไปแก้ที่ harness
Chapter 03
Context Engineering

Part: Part 1 · Foundations — รู้จักโมเดลและบริบทอย่างแท้จริง

Why this chapter exists: นี่คือทักษะที่แยก AI engineer ทั่วไปออกจาก Harness Engineer เพราะระบบ agent จะชนข้อจำกัด context เร็วกว่าที่คนส่วนใหญ่คิด.

Mentor lens: บทนี้คือแกนของสาย Harness Engineer เพราะมันสอนให้คุณบริหารพื้นที่รับรู้ของโมเดลอย่างจงใจ แทนการโยนทุกอย่างเข้า context แล้วค่อยหวังว่าจะไม่พัง.

Capstone translation: ใน capstone บทนี้ควรเปลี่ยนเป็น context budget table, trigger rules สำหรับ compaction และ policy ว่าอะไรอยู่ in-context อะไรอยู่ external memory.

เรื่องที่ต้องเรียน

  • Context window เป็น scarce resource — คิดเหมือน CPU cache ไม่ใช่ disk
  • Context budget allocation — system, history, tool defs, output
  • Lost in the middle problem
  • Just-in-time context loading
  • Context compaction strategies — micro/auto/full compact
  • Caching — prompt caching, KV cache

What the learner should be able to do

  • ออกแบบ context layout ของ session ยาวได้
  • รู้ว่าเมื่อไหร่ต้อง compact และเมื่อไหร่ต้อง offload
  • ประมาณ cost ของ session ได้ก่อนรันจริง
Chapter 04
Tool / Function Calling Design

Part: Part 2 · Building Blocks of a Harness

Why this chapter exists: Agent จะฉลาดขึ้นจริงก็ต่อเมื่อเครื่องมือของมันชัด ปลอดภัย และสื่อความหมายดีพอให้โมเดลใช้ถูกตั้งแต่ครั้งแรก.

Mentor lens: บทนี้เปลี่ยนวิธีคิดจากมอง tool เป็น feature ไปสู่การมอง tool เป็น interface contract ที่มี privilege, context cost และ failure mode ของตัวเอง.

Capstone translation: เปลี่ยนบทนี้เป็น tool registry พร้อม schema tests, permission metadata และ result shaping modes ที่มี concise/raw ชัดเจน.

เรื่องที่ต้องเรียน

  • Tool schema design — JSON Schema, additionalProperties: false สำคัญอย่างไร
  • Tool description writing — เขียนแบบไหนให้โมเดลเลือกใช้ถูก
  • Few but powerful vs many specific tools — tradeoff
  • Tool composition
  • Permission tiers per tool
  • Tool result formatting — output ใหญ่ ๆ ฆ่า context

What the learner should be able to do

  • ออกแบบ tool ใหม่ได้แบบ eval-driven
  • เขียน tool description ที่โมเดลใช้ถูกตั้งแต่ครั้งแรก
  • เข้าใจว่า power tool ต้องมาคู่กับ permission และ output discipline
Chapter 05
The Agentic Loop / Query Engine

Part: Part 2 · Building Blocks of a Harness

Why this chapter exists: Query engine คือจุดรวมของ prompt, tools, memory, context, permissions และ recovery logic ถ้าลูปนี้ออกแบบไม่ดี ทุกชั้นที่เหลือจะโดนลากลง.

Mentor lens: บทนี้สอนให้คุณมองระบบ agent เป็นวงจรการตัดสินใจ ไม่ใช่ข้อความโต้ตอบเดี่ยว ๆ และช่วยให้คุณรู้ว่า failure จำนวนมากเกิดที่ loop design ไม่ใช่ที่ model intelligence อย่างเดียว.

Capstone translation: บทนี้ควรถูก encode เป็น state diagram, finish reason taxonomy, recovery matrix และ loop guardrails ใน runtime ของคุณ.

เรื่องที่ต้องเรียน

  • Agentic patterns พื้นฐาน: ReAct, Reflection, Plan-and-Execute, Tree-of-Thought
  • Stop conditions — explicit mechanism ของ task done
  • Token budget exhaustion handling
  • Tool failure recovery
  • Step limits และ circuit breakers
  • State machine vs free-form loop

What the learner should be able to do

  • ออกแบบ loop ที่ไม่หลุด ไม่วน และ recover ได้
  • รู้ว่าเมื่อไหร่ใช้ ReAct vs Plan-and-Execute vs Reflection
  • ซ่อนความวุ่นวายภายในจากผู้ใช้ด้วย recovery ที่ดี
Chapter 06
Memory Architecture

Part: Part 2 · Building Blocks of a Harness

Why this chapter exists: เมื่อ session ข้ามวัน ข้าม repo หรือข้ามโปรเจค ความต่างระหว่าง toy agent กับใช้งานจริงอยู่ที่ memory layer แทบทั้งหมด.

Mentor lens: บทนี้บอกชัดว่า memory ไม่ใช่ magic feature ของโมเดล แต่เป็นวิธีที่ harness จัดการสิ่งที่ควรอยู่ในหัวของระบบต่อเนื่องข้าม turn และข้าม session.

Capstone translation: เปลี่ยนบทนี้ให้เป็น memory map, write discipline, consolidation rules และ source-of-truth policy สำหรับข้อมูลแต่ละชนิด.

เรื่องที่ต้องเรียน

  • 3-layer memory model ของ Claude Code: in-context, file-based, static config
  • Self-healing memory — treating memory as hint, not truth
  • Episodic vs Semantic vs Procedural memory
  • AutoDream / Memory consolidation
  • Append-only logs
  • Vector memory / RAG — เมื่อไหร่ใช้, เมื่อไหร่ไม่ใช้

What the learner should be able to do

  • ออกแบบ memory system ที่ persistent ข้าม session ได้
  • อธิบายได้ว่าทำไมใส่ทุกอย่างลง vector DB คือ anti-pattern
  • เขียน memory layer ที่ทำงานร่วมกับ context budget จำกัดได้
Chapter 07
Context Management & Compaction

Part: Part 2 · Building Blocks of a Harness

Why this chapter exists: ทุก session ที่ยาวพอจะชน context window และถ้าไม่มี context manager ที่ดี agent จะค่อย ๆ เลอะจนทำงานต่อไม่ได้.

Mentor lens: บทนี้สอนว่าสิ่งสำคัญไม่ใช่แค่ย่อ conversation แต่คือการรักษาความต่อเนื่องของงานหลังย่อเสร็จ และรู้ว่าอะไรคือแก่นที่ห้ามหาย.

Capstone translation: บทนี้ควรกลายเป็น compaction tiers, token thresholds, re-injection classes และ post-compact sanity checks.

เรื่องที่ต้องเรียน

  • MicroCompact — แก้ cached content in-place
  • AutoCompact — structured summary, reserve token buffer
  • Full Compact — บีบ conversation ทั้งก้อน
  • Selective re-injection — file caps, plan, skill schemas
  • Compaction triggers — token threshold, idle time, user command
  • Circuit breakers — กัน compact loop infinite

What the learner should be able to do

  • เขียน context manager ที่ตรวจ token budget ได้แบบ real-time
  • ออกแบบ compaction ที่ไม่ทำให้ agent ลืมสิ่งสำคัญ
  • รู้ว่าเมื่อไหร่ควร compact vs spawn sub-agent ใหม่
Chapter 08
Multi-Agent Systems & Sub-agents

Part: Part 3 · Advanced Orchestration

Why this chapter exists: ปัญหาบางอย่างใหญ่เกิน agent เดียว แต่หลายปัญหากลับแย่ลงเมื่อใช้หลาย agent เพราะ cost, coordination overhead และ context corruption สูงขึ้น.

Mentor lens: บทนี้ทำให้คุณไม่ตกหลุม 'หลาย agent ต้องดีกว่า' และสอนให้ใช้การแตกงานเมื่อมันเพิ่ม throughput หรือ isolation จริงเท่านั้น.

Capstone translation: เปลี่ยนบทนี้ให้เป็น delegation policy, child-brief template, per-lane budgets และ merge criteria.

เรื่องที่ต้องเรียน

  • Single-agent vs Multi-agent — เมื่อไหร่ที่ multi-agent ทำให้ระบบแย่ลง
  • Manager pattern — orchestrator เรียก worker
  • Decompose-Solve-Merge
  • Critic / Evaluator-Optimizer pattern
  • Sub-agent execution models: Fork, Teammate, Worktree
  • Context firewall

What the learner should be able to do

  • รู้ว่าเมื่อไหร่ไม่ควร multi-agent
  • ออกแบบ sub-agent ที่ scope แคบ ปลอดภัย และรวมผลได้
  • เข้าใจ trade-off ของ cost, throughput, และ safety
Chapter 09
MCP (Model Context Protocol) & External Integrations

Part: Part 3 · Advanced Orchestration

Why this chapter exists: ถ้าจะเป็น Harness Engineer มืออาชีพ คุณต้องอ่าน spec ได้ ออกแบบ tool surface ได้ และเขียน MCP server เองได้.

Mentor lens: บทนี้ทำให้คุณมอง MCP เป็น protocol boundary และ control surface ไม่ใช่เพียงทางลัดในการต่อของเข้ากับโมเดล.

Capstone translation: บทนี้ควรลงท้ายที่ MCP server MVP หนึ่งตัว พร้อม capability map, threat model และ contract tests.

เรื่องที่ต้องเรียน

  • MCP architecture — host, client, server, JSON-RPC 2.0 over stdio/HTTP
  • Three primitives: Tools, Resources, Prompts
  • Capability discovery
  • Transport — stdio (local), HTTP/SSE (remote)
  • MCP security model — treat all tool inputs as untrusted
  • Threats: rug-pull attacks, prompt injection ผ่าน tool result, lookalike tools

What the learner should be able to do

  • เขียน MCP server ที่พร้อมใช้งานจริงได้
  • ออกแบบ tool surface ให้ปลอดภัยและประหยัด context
  • เข้าใจว่าทำไม MCP แก้ N×M integration problem
Chapter 10
Permission, Sandboxing & Security

Part: Part 3 · Advanced Orchestration

Why this chapter exists: Harness Engineer ต้องคิดเรื่อง security ตั้งแต่ design stage เพราะเมื่อระบบมี tool use แล้ว attack surface จะขยายทันที.

Mentor lens: บทนี้ย้ำว่าทุกครั้งที่ agent มีอำนาจเพิ่ม คุณกำลังสร้าง security boundary ใหม่ และต้องคิดเรื่อง blast radius ควบคู่กับ convenience เสมอ.

Capstone translation: เปลี่ยนบทนี้เป็น threat model, permission matrix, sandbox profile และ approval UX ที่อธิบายความเสี่ยงได้ชัด.

เรื่องที่ต้องเรียน

  • Threat model สำหรับ AI agent — prompt injection, tool poisoning, exfiltration via tool composition
  • Permission tiers per tool — read-only / state-changing / dangerous
  • Allowlist vs context-aware permission
  • Critic pattern for permission
  • Sandboxing — container, VM, seccomp, restricted filesystem
  • Dangerous flags — --yolo, --accept-all

What the learner should be able to do

  • เขียน permission layer ที่ adaptive และ context-aware
  • รู้จัก attack vectors หลักของ tool-using agents
  • ออกแบบ sandbox ที่บาลานซ์ usability กับ safety
Chapter 11
Evaluation-Driven Development

Part: Part 4 · Reliability & Production

Why this chapter exists: Eval คือ methodology หลักของการพัฒนา agent เพราะพฤติกรรมจำนวนมาก non-deterministic และ open-ended กว่า software ปกติ.

Mentor lens: บทนี้เปลี่ยนการพัฒนา agent จากการชิม output ด้วยตา ไปสู่การตัดสินด้วยพฤติกรรมที่วัดซ้ำได้และรองรับ regression.

เรื่องที่ต้องเรียน

  • ทำไม eval ของ agent ≠ unit test ปกติ
  • Three-layer eval stack: what you evaluate, how you grade, what grounds it
  • Deterministic checks — unit tests สำหรับ agent
  • LLM-as-a-Judge — เมื่อไหร่ใช้ได้, bias ที่ต้องระวัง
  • Error analysis as development methodology
  • Online vs Offline eval

What the learner should be able to do

  • เขียน eval ก่อนเขียน feature ได้เป็นนิสัย
  • มี test pyramid สำหรับ agent
  • รู้ข้อจำกัดของ LLM-as-a-Judge และใช้อย่างมีวินัย
Chapter 12
Observability & Telemetry

Part: Part 4 · Reliability & Production

Why this chapter exists: Production harness แยกจาก toy project ตรงที่มันไม่เพียงรันได้ แต่บอกได้ด้วยว่ากำลังเกิดอะไรขึ้น ทำไมเกิด และกระทบผู้ใช้อย่างไร.

Mentor lens: บทนี้สอนให้คุณมอง traces, logs และ metrics เป็นวิธีทำให้ระบบ agent เล่าเรื่องตัวเองได้เวลาเก่งขึ้นหรือเริ่มหลุดทาง.

Capstone translation: เปลี่ยนบทนี้เป็น trace tree, key metrics, privacy-aware logging policy และ replay workflow.

เรื่องที่ต้องเรียน

  • Tracing for agent — span สำหรับ LLM call, tool call, sub-agent
  • Three pillars: Logs, Metrics, Traces ในบริบท agent
  • OpenTelemetry สำหรับ LLM — semantic conventions
  • Token accounting — input/output/cached tokens, cost per session

What the learner should be able to do

  • มี dashboard ที่ตอบได้ว่า agent วันนี้ทำงานดีแค่ไหน
  • debug ปัญหา rare cases ได้จาก trace และ replay
Chapter 13
Failure Recovery & Self-Healing

Part: Part 4 · Reliability & Production

Why this chapter exists: ความอึดของ agent ไม่ได้วัดจากจำนวนฟีเจอร์ แต่วัดจากวิธีที่มันตอบสนองเมื่อโลกจริงไม่เป็นไปตามแผน.

Mentor lens: บทนี้ฝึกให้คุณเปลี่ยน failure ให้กลายเป็น design input ของรอบถัดไป แทนที่จะปล่อยให้มันเป็นเหตุบังเอิญที่คอยย้อนมารบกวนผู้ใช้อีก.

Capstone translation: บทนี้ควรถูกบันทึกเป็น failure taxonomy, recovery matrix, degraded modes และ postmortem template.

เรื่องที่ต้องเรียน

  • Failure modes ของ agent: tool error, token exhaustion, hallucinated tool call, infinite loop, context drift
  • Recovery strategies — retry, exponential backoff, fallback tool, ask for help
  • Mitchell Hashimoto's principle — engineer the environment so the agent physically cannot make the mistake again
  • Update AGENTS.md / CLAUDE.md as feedback loop
  • Computational vs inferential controls
  • Back-pressure verification

What the learner should be able to do

  • เขียน harness ที่อึดและ absorb failures ได้ดี
  • เปลี่ยน recurring failures เป็น engineering fixes ถาวร
  • ออกแบบ controls หลายชั้นก่อนผลลัพธ์ถึงผู้ใช้
Chapter 14
Cost & Performance Optimization

Part: Part 4 · Reliability & Production

Why this chapter exists: Agent ที่ทำงานได้แต่แพงหรือช้าเกินไปคือ prototype ที่ยังไม่ผ่านเกณฑ์ productization.

Mentor lens: บทนี้สอนให้คุณรักข้อจำกัดของ token budget แทนการใช้โมเดลแพงสุดทุกครั้ง เพราะระบบจะ scale ได้จริงก็ต่อเมื่อ economics และ latency อยู่ในระดับที่ยอมรับได้.

Capstone translation: เปลี่ยนบทนี้เป็น route policy, cache plan, cost ledger, latency waterfall และ budget alerts.

เรื่องที่ต้องเรียน

  • Token economics — input vs output cost, cached vs fresh
  • Model routing — เล็กก่อน, ใหญ่เมื่อจำเป็น
  • Prompt caching at scale
  • Latency optimization — streaming, parallel tool calls, speculative execution
  • Batch API — สำหรับงานที่ไม่ realtime
  • Result caching — semantic cache, exact match cache

What the learner should be able to do

  • ลด cost ลงอย่างมีวินัยโดยไม่เสียคุณภาพหลัก
  • มี cost dashboard per-feature และ per-user
  • เข้าใจ trade-off ระหว่าง compute time กับ accuracy
