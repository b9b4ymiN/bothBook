บทที่ 06 / Chapter 06

Memory Architecture

บทนี้ไม่ได้ต้องการให้คุณจำศัพท์ได้มากขึ้น แต่ต้องการให้คุณเริ่มตัดสินใจเชิงระบบได้แม่นขึ้นเมื่อสร้างหรือรีวิว harness ของจริง.

The Core Idea · แก่นของบท

สิ่งที่บทนี้กำลังเปลี่ยนในวิธีคิดของคุณ

บทนี้บอกชัดว่า memory ไม่ใช่ magic feature ของโมเดล แต่เป็นวิธีที่ harness จัดการสิ่งที่ควรอยู่ในหัวของระบบต่อเนื่องข้าม turn และข้าม session.

ความสับสนหลักคือเอา append-only history, semantic memory และ static policy ไปเก็บรวมกัน แล้วหวังว่าจะ query กลับออกมาอย่างมีความหมาย.

การเรียนบทนี้ให้เข้าใจง่ายที่สุดคืออ่านผ่านคำถามสามข้อ: หนึ่ง ปัญหานี้เกิดจาก layer ไหนกันแน่; สอง ถ้าปล่อยไว้จะไหลไปกระทบ reliability, safety, cost หรือ operator experience อย่างไร; และสาม เราจะเก็บหลักฐานอะไรเพื่อพิสูจน์ว่าการออกแบบใหม่ดีกว่าเดิม. ถ้าคุณตอบสามข้อนี้ได้ บทนี้จะไม่เป็นแค่ความรู้ แต่จะกลายเป็นเครื่องมือในการตัดสินใจ.

Harness implication

เอกสารที่ดีสำหรับสายนี้ต้องทำให้ผู้อ่านแปลแนวคิดออกมาเป็น implementation shape ได้. ถ้าบทหนึ่งยังไม่ทำให้คุณเห็นว่าจะไปลงใน code, config, tool boundary, eval หรือ trace ตรงไหน แปลว่าบทยังไม่ลงลึกพอ.

Common confusions ที่ควรเคลียร์ก่อนอ่านต่อ

  • ความสับสนหลักคือเอา append-only history, semantic memory และ static policy ไปเก็บรวมกัน แล้วหวังว่าจะ query กลับออกมาอย่างมีความหมาย.
  • อย่าปล่อยให้คำว่า model capability กลบคำถามเรื่อง environment design, privilege boundaries และ runtime policy.
  • อย่าตัดสินจากเดโมครั้งเดียว เพราะบทนี้เกี่ยวกับพฤติกรรมที่ต้องเสถียรเมื่อ workload โตขึ้นและเงื่อนไขแย่ลง.
  • อย่าถือว่าการอธิบาย intuition เพียงพอ ถ้ายังไม่มีตัวอย่างว่าระบบจริงจะเปลี่ยนอย่างไรหลังนำแนวคิดนี้ไปใช้.
Anchor artifact · สิ่งที่ควรจับต้องได้

หนึ่ง artifact ที่ช่วยให้บทนี้ไม่ลอย

แทนที่จะปล่อยให้บทนี้อยู่ในระดับคำอธิบายอย่างเดียว ส่วนนี้ตั้งใจให้เป็นตัวอย่าง artifact ที่ผู้อ่านสามารถใช้เป็นแบบฝึกคิดหรือดัดแปลงเข้ากับ capstone ได้ทันที. มันไม่จำเป็นต้องเป็น implementation สุดท้าย แต่ควรพอให้เห็นรูปทรงของการออกแบบจริง.

ตัวอย่างนี้ทำให้ผู้อ่านเห็นความต่างระหว่างสิ่งที่ "ควรจำ" กับสิ่งที่ "ควรเก็บเป็น pointer".

เวลาคุณอ่าน artifact นี้ ให้ถามต่อว่าในระบบของคุณอะไรคือ version ที่เล็กที่สุดของมันที่ควรเกิดขึ้นภายในสัปดาห์นี้. การหาคำตอบข้อนี้ได้คือจุดที่บทเรียนเริ่มเปลี่ยนจาก reading material เป็น engineering momentum.

Topic deep dive · 01

3-layer memory model ของ Claude Code: in-context, file-based, static config

หัวข้อนี้สำคัญในบท Memory Architecture เพราะมันบอกว่าทีมกำลังใช้ระบบแบบมีข้อจำกัดที่ชัดเจน หรือยังปล่อยให้โมเดลเดาในพื้นที่ที่ควรถูกออกแบบไว้ล่วงหน้า. บทนี้บอกชัดว่า memory ไม่ใช่ magic feature ของโมเดล แต่เป็นวิธีที่ harness จัดการสิ่งที่ควรอยู่ในหัวของระบบต่อเนื่องข้าม turn และข้าม session.

ถ้าคุณกำลังสร้างของจริง สิ่งแรกที่ควรถามไม่ใช่แค่ '3-layer memory model ของ Claude Code: in-context, file-based, static config คืออะไร' แต่คือมันควรไปนั่งอยู่ในชั้นไหนของระบบ และควรทิ้งสัญญาณอะไรไว้เมื่อเริ่มล้มเหลว. สำหรับหัวข้อนี้ สัญญาณที่มักโผล่ก่อนคือ session ยาวแล้วคุณภาพตก, context overflow, repeated forgetting, cost พุ่ง.

ทำไมคนจำนวนมากพลาดตรงนี้

ความสับสนหลักคือเอา append-only history, semantic memory และ static policy ไปเก็บรวมกัน แล้วหวังว่าจะ query กลับออกมาอย่างมีความหมาย.

เมื่อทีมยังไม่แยกเรื่องนี้ออกมาอย่างชัดเจน หัวข้ออย่าง 3-layer memory model ของ Claude Code: in-context, file-based, static config มักถูกฝังอยู่ใน prompt prose, ความเคยชินของคนใช้เครื่องมือ, หรือการตัดสินใจเฉพาะหน้าของ runtime. ผลคือระบบดูเหมือนทำงานได้ แต่เมื่อ workload โตขึ้น ปัญหาจะโผล่ในรูปของต้นทุนที่พุ่ง คุณภาพที่แกว่ง หรือพฤติกรรมที่อธิบายไม่ได้.

ตัวอย่างในระบบจริง

ใน personal knowledge agent ที่ดี ความทรงจำเกี่ยวกับ preference, active project state และ canonical docs ต้องอยู่คนละชั้น ไม่เช่นนั้น retrieval จะคืนค่าปนกันจนใช้การไม่ได้.

ให้ใช้ภาพนี้เป็นจุดยึดเวลาคุณคิดถึง 3-layer memory model ของ Claude Code: in-context, file-based, static config: ถ้าคุณยังไม่เห็นว่ามันเปลี่ยน trace, config, schema, memory rule หรือ approval flow ตรงไหน แปลว่าหัวข้อนี้ยังถูกเก็บไว้ในชั้นคำอธิบายมากกว่าชั้น implementation.

สิ่งที่ Harness Engineer ต้องตัดสินใจ

  • หัวข้อนี้ควรถูก encode เป็น artifact แบบใดก่อน: context budget table, compaction trigger rules, re-injection policy.
  • จุดใดคือ trust boundary หรือ cost boundary ที่หัวข้อนี้กำลังแตะอยู่.
  • ถ้าระบบพังเพราะเรื่องนี้ ทีมจะรู้จากสัญญาณใดก่อน: session ยาวแล้วคุณภาพตก, context overflow, repeated forgetting, cost พุ่ง.
  • อะไรคือ deterministic control ขั้นต่ำที่ควรมี และอะไรคือส่วนที่ปล่อยให้ model reasoning ช่วยตัดสินใจได้.

ตัวอย่างคำถาม review ที่ควรถามใน PR หรือ design doc

  • ข้อมูลชิ้นนี้จำเป็นต้องอยู่ in-context ตอนนี้จริงหรือควรถูกสรุปหรือโหลดเมื่อจำเป็นเท่านั้น
  • เรากำลังพึ่งพาให้โมเดลเดาเรื่อง 3-layer memory model ของ Claude Code: in-context, file-based, static config มากเกินไปหรือไม่.
  • ข้อมูลหรืออำนาจที่เกี่ยวกับหัวข้อนี้อยู่ใน layer ที่เหมาะสมหรือยัง.
  • ถ้า workload โตขึ้น 10 เท่า หัวข้อนี้จะกลายเป็น bottleneck เรื่องใดก่อน.
  • เรามีหลักฐานใดบ้างที่จะใช้พิสูจน์ว่าการเปลี่ยนแปลงตรงนี้ทำให้ระบบดีขึ้นจริง.

แปลเป็น capstone วันนี้

เปลี่ยนบทนี้ให้เป็น memory map, write discipline, consolidation rules และ source-of-truth policy สำหรับข้อมูลแต่ละชนิด.

ถ้าคุณอ่านบทนี้เพื่อเอาไปใช้จริงทันที ให้เลือกเพียงหนึ่ง artifact ที่เกี่ยวกับ 3-layer memory model ของ Claude Code: in-context, file-based, static config แล้วลงมือแก้ภายในวันนี้. ความเข้าใจจะเริ่มนิ่งเมื่อมันเปลี่ยนสิ่งที่อยู่ใน repo, dashboard, runtime หรือ review process ของคุณ.

เวลาระบบเริ่มโต หัวข้ออย่าง Self-healing memory — treating memory as hint, not truth มักเป็นจุดที่แยกระหว่างเดโมที่ดูฉลาดกับ harness ที่ใช้งานได้จริง. ใน personal knowledge agent ที่ดี ความทรงจำเกี่ยวกับ preference, active project state และ canonical docs ต้องอยู่คนละชั้น ไม่เช่นนั้น retrieval จะคืนค่าปนกันจนใช้การไม่ได้.

ความสับสนหลักคือเอา append-only history, semantic memory และ static policy ไปเก็บรวมกัน แล้วหวังว่าจะ query กลับออกมาอย่างมีความหมาย.

เมื่อทีมยังไม่แยกเรื่องนี้ออกมาอย่างชัดเจน หัวข้ออย่าง Vector memory / RAG — เมื่อไหร่ใช้, เมื่อไหร่ไม่ใช้ มักถูกฝังอยู่ใน prompt prose, ความเคยชินของคนใช้เครื่องมือ, หรือการตัดสินใจเฉพาะหน้าของ runtime. ผลคือระบบดูเหมือนทำงานได้ แต่เมื่อ workload โตขึ้น ปัญหาจะโผล่ในรูปของต้นทุนที่พุ่ง คุณภาพที่แกว่ง หรือพฤติกรรมที่อธิบายไม่ได้.

มุมมองแบบผู้รีวิวระบบ

เวลาอ่านหัวข้อนี้ ให้ลองสมมติว่าคุณเป็น reviewer ที่ต้องอนุมัติ design ของทีม. คุณจะไม่ถามแค่ว่าเข้าใจคำศัพท์นี้ไหม แต่จะถามว่า boundary ถูกวางไว้ถูกชั้นหรือยัง และ evidence ที่จะพิสูจน์การตัดสินใจนี้อยู่ตรงไหน.

วิธีคิดแบบ reviewer นี้ทำให้ Vector memory / RAG — เมื่อไหร่ใช้, เมื่อไหร่ไม่ใช้ กลายเป็นเครื่องมือในการตั้งคำถามที่ดีขึ้น ไม่ใช่แค่เนื้อหาสำหรับจดจำ.

สิ่งที่ Harness Engineer ต้องตัดสินใจ

  • หัวข้อนี้ควรถูก encode เป็น artifact แบบใดก่อน: memory map, source_ref policy, consolidation job, storage decision table.
  • จุดใดคือ trust boundary หรือ cost boundary ที่หัวข้อนี้กำลังแตะอยู่.
  • ถ้าระบบพังเพราะเรื่องนี้ ทีมจะรู้จากสัญญาณใดก่อน: stale facts, contradictory notes, retrieval noise, memory write ที่ย้อนตรวจที่มาไม่ได้.
  • อะไรคือ deterministic control ขั้นต่ำที่ควรมี และอะไรคือส่วนที่ปล่อยให้ model reasoning ช่วยตัดสินใจได้.

  • สิ่งนี้ควรถูกเก็บเป็น fact, pointer, preference หรือ policy กันแน่

Topic deep dive · 07

Memory write discipline — ห้าม dump content ใน index

หัวข้อนี้สำคัญในบท Memory Architecture เพราะมันบอกว่าทีมกำลังใช้ระบบแบบมีข้อจำกัดที่ชัดเจน หรือยังปล่อยให้โมเดลเดาในพื้นที่ที่ควรถูกออกแบบไว้ล่วงหน้า. บทนี้บอกชัดว่า memory ไม่ใช่ magic feature ของโมเดล แต่เป็นวิธีที่ harness จัดการสิ่งที่ควรอยู่ในหัวของระบบต่อเนื่องข้าม turn และข้าม session.

ถ้าคุณกำลังสร้างของจริง สิ่งแรกที่ควรถามไม่ใช่แค่ 'Memory write discipline — ห้าม dump content ใน index คืออะไร' แต่คือมันควรไปนั่งอยู่ในชั้นไหนของระบบ และควรทิ้งสัญญาณอะไรไว้เมื่อเริ่มล้มเหลว. สำหรับหัวข้อนี้ สัญญาณที่มักโผล่ก่อนคือ stale facts, contradictory notes, retrieval noise, memory write ที่ย้อนตรวจที่มาไม่ได้.
